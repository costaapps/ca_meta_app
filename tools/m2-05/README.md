# M2.05 durable work harness

The harness uses a fresh UUID-named Compose project, volume, loopback port, temporary init SQL and synthetic credentials on each run. It pins MariaDB 11.8.8 by digest and uses Node 24.22.2/npm 11.19.1. Cleanup addresses only the project created by this script. It does not inspect, stop or remove another Compose project.

From the repository root on Windows:

```powershell
powershell -ExecutionPolicy Bypass -File tools/m2-05/run-mariadb-tests.ps1
```

The script sets up separate least-privilege synthetic migrator and runtime accounts, compiles the API test tree, and runs `durable-work.integration.spec.js`, `m3-05-onboarding.integration.spec.js` and `m3-06-meta-assets.integration.spec.js` with `M2_DURABLE_WORK_TEST=1`, followed by `m3-01-job-authorization.integration.spec.js` with `M2_DURABLE_WORK_TEST=1`, `m3-02-db.integration.spec.js` with `M3_02_DB_TEST=1`, `m3-07-credential-vault.integration.spec.js` with `M2_DURABLE_WORK_TEST=1`, `m3-09-credential-lifecycle.integration.spec.js` with `M3_09_TEST=1`, `m3-03-magic-link-identity.integration.spec.js` with `M3_03_TEST=1`, and `m3-11-legacy-import.integration.spec.js` with `M3_11_TEST=1`. The durable-work and M3.05 onboarding fixtures use the current ordered registry, including schema v22. The disposable init grants the migrator `DELETE` only on `ca_meta_onboarding_coexistence_locks`; the M2.03 harness separately verifies that a fresh schema pauses safely before the trigger when this grant is absent, then resumes after a synthetic root grants it. Historical package assertions such as the M3.03 v14 and M3.11 v15 checks remain pinned to their target migration. The M3.01 fixture authorizes a claimed asset-refresh job through the real MySQL claim, asset-authorization, and active service-grant queries, then denies a forged claim, changed payload, and revoked grant using synthetic rows. The onboarding fixture checks migration v10, tenant/session ownership, tenant-scoped idempotency, one-use state consumption and digest-only persistence using synthetic rows. The M3.03 fixture applies schema v14 and checks single-use server proof references, email/principal non-reassignment, active-membership requirement, revocation, re-verification and append-only identity events. The M3.11 schema v15 fixture verifies metadata-only claims and durable checkpoint resume. The session fixture asserts that a Suite4 embed mode survives the actual MySQL session insert. The full API/root suite is a separate candidate gate and is not repeated by this harness. No production/staging database, Meta API, provider account, real tenant data, or provider credential is used.

The M3.06 fixture covers concurrent upsert/shared assets, confirmed scopes and grants, typed Instagram-to-Page relation persistence, omitted-grants preservation versus explicit revocation, cross-tenant FK rejection and quarantine, exact external IDs above 2^53, and rollback after outbox staging. Its JUnit and LCOV reports are emitted as `m3-06-meta-assets.*`. The M3.01 job-authorization fixture emits `m3-01-job-authorization.*`; the M3.02 portal-session fixture emits `m3-02-portal-session.*`. These report sets are uploaded by the M2.08 MariaDB workflow.

The M3.07 schema v11 fixture uses runtime-generated synthetic keys/markers to cover tenant-bound ciphertext, metadata-only audit, one active rotation lease, checkpoint resume after worker recreation, and a full disposable MariaDB logical dump/drop/restore round trip. The harness generates the active v3 test key in memory and passes it through a process-only environment variable to M3.07 and M3.09, since both fixtures share the disposable database and its singleton active-key version. Standalone fixtures still generate an in-memory key when no shared database key exists. The v3 key is not printed or written to repository files. M3.07 confirms that the dump, persisted ciphertext rows, API/test build artifacts, and emitted JUnit/LCOV reports do not contain a marker in plaintext; a key ring missing the restored envelope's version is denied, while the authorized retained key decrypts the restored records. Reports are emitted as `m3-07-credential-vault.*`; the local exercise does not certify production backup access controls, physical media, KMS custody, retention, or restore procedures.

The M3.09 schema v13 fixture covers one per-credential schedule lease and idempotent inspection enqueue, exact credential-to-asset reauth impacts, confirmed revocation versus non-revoking expired/action-required observations, bounded paginated impact reads, and current/stale vault replacement fences. It uses only runtime-generated synthetic credentials and the same ephemeral active test key as M3.07 when sharing the disposable database; it emits `m3-09-credential-lifecycle.*` reports. The M3.03 schema v14 fixture stores only keyed email hashes and proof-reference hashes, requires an existing active principal membership, prevents proof replay and cross-principal reassignment, records fixed event/actor enums in an append-only ledger, and supports revocation plus same-principal re-verification. It emits `m3-03-magic-link-identity.*` reports.

The M3.11 schema v15 fixture interrupts after an item/checkpoint transaction commits, resumes from the durable MariaDB cursor, replays the same source/payload HMAC without duplicating the metadata-only claim, and quarantines a changed payload under the same source HMAC. The ledger stores HMAC references, internal tenant/app/target references and fixed metadata only; it does not persist source row IDs, provider IDs, credentials or raw source payload. JUnit and LCOV reports are emitted as `m3-11-legacy-import.*` and uploaded with the other M2.05 fixtures.

The M2.05/M3.06/M3.07/M3.09 MariaDB scenarios check:

- Migration chain v1/v2/v3 and the additive v3 schema, including job claim, tenant/resource, tenant+lane candidate, ambiguous lease and replay audit indexes, plus one persistent dispatch cursor per lane.
- Same idempotency key/body returns the existing job; the same key with a different payload hash is rejected.
- Inbox persists before returning, routes through the server-owned app configuration row, enqueues in the same transaction, deduplicates semantic redelivery despite a new receive timestamp/correlation/protected handle, and rejects changed semantic metadata.
- Outbox row plus delivery job and a synthetic local write roll back together. A repeated event is deduplicated. An uncertain external outcome or expired ambiguous lease marks both job and outbox projection `UNKNOWN` atomically, with no automatic retry.
- Two claimers serve another tenant while one tenant has a lease active; a blocked asset scope does not block a second asset scope in the same tenant.
- A per-lane cursor is locked before candidate discovery and advances atomically with a successful claim. Sequential completion lets tenant B claim while tenant A still has backlog; concurrent workers serialize and re-read the cursor before selecting their turns.
- Concurrent claims for one tenant/resource never receive the same active scope. A real child process claims an inbox job and is killed without ACK; a replacement requeues it after expiry/backoff. A second child persists a quarantined `provider.unclassified` inbox event, is killed before ACK, and the replacement repeats `InboxService.persist`; the app-config/provider-event key returns a duplicate and leaves exactly one row. This synthetic local effect uses the existing schema and no provider call. Expired safe leases are delayed, stale fencing tokens cannot ACK, and attempt/budget exhaustion reaches a redacted DLQ.
- A handler remains leased beyond the original TTL through heartbeat while SIGTERM stops claims and drains it. The worker aborts at the per-type deadline and stops heartbeats; cooperative cancellation gets a bounded grace. A handler still pending after that grace is finalized `UNKNOWN` without retry, late results cannot finalize it, and that worker exits its claim loop to avoid accumulating abandoned handlers.
- DLQ stores safe reason/action fields only. Inbox projections follow the effective job result in the same transaction, including `UNKNOWN` and retry exhaustion into `DEAD_LETTER`. An authorized `INBOX_PROCESS` replay resets only its exact tenant-scoped dead-letter projection to `PENDING` in the enqueue transaction; successful finalization reaches `PROCESSED`, and duplicate replay leaves the projection unchanged. The default replay port denies. An explicit exact tenant/job/resource/operator grant can authorize a dry-run preview without enqueueing, or requeue safe work idempotently; database scope mismatch is denied, expired grants and ambiguous effects cannot replay, audit writes are append-only, and the harness never executes a provider handler.
- An unforced MariaDB `EXPLAIN` selects `ix_ca_meta_job_ambiguous_expired` for the expired ambiguous lease sweep after a synthetic mixed-state fixture and `ANALYZE TABLE`.
- The claim harness seeds 5,000 ready historical projection jobs and measures two concurrent urgent webhook claims with a 2-second bound. Separate unforced plans check the global urgent lane pass and both tenant/lane ready and expired lease lookups; lane-priority queries avoid scanning lower-priority history to find urgent work. The dispatch cursor is fixed-size state per lane, so tenant fairness does not aggregate terminal job history.

`MAX_ACTIVE_JOBS_PER_TENANT = 4`, `MAX_WAITING_JOBS_PER_TENANT = 1000`, cancellation grace, handler deadlines, retry delays and elapsed/attempt limits are synthetic implementation defaults aligned to M1.09 planning; they are not Meta quotas, measured production limits, or a provider contract. A handler should honor its `AbortSignal`. If it does not settle within the configured grace, the attempt becomes terminal `UNKNOWN`, the worker stops claiming and reports a process failure, and any late completion is ignored. Work without a registered handler remains unclaimed. The worker command is available from the API image (`npm run start:worker --workspace=@ca-meta/api`); this package intentionally registers no onboarding/provider handler.

The API Nest module closes the lazy durable-work pool through `OnModuleDestroy`; a focused application-context test covers that hook without rerunning the M2.02 HTTP suite.

Each database fixture prints a fixed label before it runs. If a fixture fails, the harness prints only failed JUnit testcase names, source file basenames, and a matching source line/column from the stack; failure messages, full stack traces, stdout and synthetic marker values stay out of the workflow log.

Replay is an internal service with no HTTP controller. `preview()` is always dry-run. `requeue()` requires the injected `ReplayAuthorizationPort` to grant an exact tenant, dead-letter, persisted resource scope, operator, action and expiry, and refuses ambiguous effects. The default port denies all requests. Requeue creates a durable job and an audit row transactionally; it does not invoke a handler or provider.
