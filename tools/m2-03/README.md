# M2.03 synthetic migration harness

The harness starts a fresh MariaDB 11.8.8 Compose project for each run. The project name, volume, credentials, generated init SQL, and loopback port are unique to the run. Cleanup targets only that project name. It does not inspect or stop any other Compose project, including the preserved `db-migrations-mariadb-1` container. The integrated registry applies ordered schema versions 1–11: M3.04 v5, M3.02 v6, M3.06 v7, M3.03 v8, M3.05 portal-session entry mode v9, M3.05 onboarding sessions v10, and M3.07 credential vault v11. Its backup/restore check verifies the complete ordered ledger, preserves migration checksums, and retains the original v1/v2 definitions.

Prerequisites: Node 24.22.2, npm 11.19.1, Docker Engine, Docker Compose v2, and network access to the pinned MariaDB image on its first run. The PowerShell harness verifies those exact versions. It uses `%LOCALAPPDATA%\Codex\runtimes\node-v24.22.2` by default; set `M2_NODE_RUNTIME_DIR` to that runtime directory when it is elsewhere.

From the repository root:

```powershell
powershell -ExecutionPolicy Bypass -File tools/m2-03/run-mariadb-tests.ps1
```

The script builds the API and test sources, creates separate least-privilege `ca_meta_api` and `ca_meta_migrator` users, runs unit and MariaDB integration checks, invokes the public `migrate:status` CLI, backs up the synthetic database with a transaction-consistent dump, restores it into a fresh database, verifies row counts/UTF-8 bytes/DATETIME(6)/ledger state, and removes only its generated project and UUID volume in `finally`. The integration fixture loads 10,000 synthetic assets and 10,000 synthetic sessions, then checks unforced tenant-scoped EXPLAIN plans after `ANALYZE TABLE`. It never writes credentials to the repository. Set `M2_03_KEEP_ENVIRONMENT=1` only when investigating locally; the script then prints the unique Compose project name and leaves that project/volume available for manual cleanup.

The migrator connection is configured only by `MIGRATION_DATABASE_*`. It must be different from `API_DATABASE_USER`; there is no fallback to runtime connection settings. The runtime account is tested for DML access and denied DDL. The migrator has database-scoped `SELECT`, `INSERT`, `UPDATE`, `CREATE`, `ALTER`, `INDEX`, `REFERENCES`, and `TRIGGER` only, without global grants or `GRANT OPTION`. Migration connections force UTC and strict SQL mode; runtime write connections must use strict mode too so overlength string IDs fail instead of truncating.

Migration steps are individually journaled by automatic fingerprints of their SQL, structured shape/configuration, and callback source, with an explicit definition version for external dependencies. DDL uses `CREATE TABLE IF NOT EXISTS` / explicit shape verification or additive `ALTER TABLE`/trigger creation. MariaDB implicitly commits DDL, so an interruption after DDL leaves `STARTED`; restart verifies the resulting schema and completes the step. Backfill updates and cursor advancement share an InnoDB transaction. The additive name migration installs N-1 INSERT/UPDATE synchronization triggers before backfill; the backfill repeatedly selects remaining NULLs, so IDs written during the DDL-to-trigger gap are recovered even when below the diagnostic cursor. Validation rejects any mismatch. Switching consumers and contract/drop work are separate versioned changes and must wait until the minimum supported API baseline moves beyond N-1; this package deliberately keeps the old `display_name` column and synchronization triggers so both versions remain compatible.

The session `EXPLAIN` uses a test-only table derived from the accepted M1.05 session shape; M3 owns the persistent session schema. Synthetic backup/restore is verified locally, but the local 11.8.8 fixture does not certify a deployed MariaDB version, production grants, production backup/restore procedures, online DDL duration, or production data shape. Those remain **Not confirmed**.
