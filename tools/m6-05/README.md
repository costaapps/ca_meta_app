# M6.05 synthetic encrypted backup and restore harness

This runner validates a transaction-consistent logical dump of the current migrated MariaDB schema, an authenticated encrypted backup artifact, and a real restore into a newly created empty schema. It then validates the restored rows through the API's credential-vault, durable-work, inbox/outbox, projection-checkpoint and portal-session stores.

## Setup and run

From the repository root in Windows PowerShell, use Node `v24.22.2`, npm `11.19.1`, Docker Desktop/Compose v2, and the pinned MariaDB image. If the worktree has no project dependencies, install them once with `npm ci --ignore-scripts`. The runner compiles the API/test TypeScript and executes only `m6-05-restore.integration.spec.js`; it does not run the API suite.

```powershell
$nodeRuntime = Join-Path $env:LOCALAPPDATA 'ca-meta-runtimes\node-v24.22.2-win-x64'
$env:Path = "$nodeRuntime;$env:Path"
$env:M6_NODE_RUNTIME_DIR = $nodeRuntime
docker info
powershell -ExecutionPolicy Bypass -File tools/m6-05/run-restore.ps1
```

## What the fixture proves

The harness migrates a fresh source schema through the compiled migration registry. It creates synthetic credentials under an old key, rotates only one batch to a new key, and leaves the migration state partial. It also seeds a pending inbox item/job, an ambiguous outbox job finalized as `UNKNOWN`, a pending projection checkpoint, and an active synthetic portal session.

The test uses `mariadb-dump --single-transaction --quick --hex-blob` to take the logical dump. It encrypts the dump in process memory with a random AES-256-GCM key, writes only the authenticated ciphertext to the runner's temporary directory, and verifies that tampering fails authentication. It decrypts the artifact in memory and pipes it to MariaDB to restore into a new, empty schema in the same disposable MariaDB instance. It checks the migration ledger, mixed key versions, key-rotation cursor, restored data, missing-key fail-closed behavior, inbox/outbox idempotency, ambiguous delivery non-replay, projection checkpoint and session revocation through application stores.

No worker/provider/Meta adapter runs. The test uses no customer data, provider credentials, Meta account, message, external company database, or production/staging service. Credential keyring material and the backup-encryption key are generated only in the test process; database account passwords are generated by the PowerShell runner. No plaintext SQL dump or key file is written to disk.

## Isolation and cleanup

Each run creates a UUID-scoped Compose project, loopback port, MariaDB volume, temporary initialization SQL and temporary encrypted artifact. The source and restore schemas share only that disposable local MariaDB instance. The runner's `finally` block removes only that project's container, network and volume, deletes its checked temporary directory, and restores environment variables/PATH. It does not inspect, stop or remove other Compose projects or volumes.

The logical artifact and database volume are deleted at the end of the local run. This verifies local cleanup only; it does not establish production retention, off-site custody, KMS recovery or expungement policy.
