# M5.02 — Connections, assets and verifiable status

## Scope

Issue [#56](https://github.com/costaapps/ca_meta_app/issues/56), implemented on `desktop/m5-02` over the M5.01 candidate `d2ccb6227c50b00c5bdfc55642f42381eb5831b1`. The focused follow-up below addresses a review finding on candidate `cdb8c7869914e5f66f9ec46f5a56998d86e72c80`.

The portal reads tenant-scoped `/connections` and `/connections/:id`. The API exposes only sanitized `displayLabel` values sourced from server-owned asset names, masks WhatsApp phone-like strings, and does not fall back to provider identifiers. Connection filtering by channel, exact configured journey, status (including stale evidence), and exact WhatsApp number is applied in SQL before cursor pagination. The UI resets filters and cursor state and clears loaded data after the authenticated context changes.

The detail view separates connection readiness, asset status, authorization, credential health, webhook/subscription, and enterprise projection. It preserves UNKNOWN, PARTIAL, stale and revoked meanings; request IDs are inside expandable support details. Four WhatsApp phone assets are represented as distinct rows, use opaque internal asset IDs in the refresh client method, and show safe masked labels or an explicit unconfirmed-label fallback.

## M1.08 identity gate and refresh

The current `SessionContext` contract contains `tenantRef` but no safe `tenantDisplayName`. The detail view keeps tenant-scoped writes unavailable unless `PortalTenantIdentityService.current.confirmed` is true. A refresh POST is issued only when that identity gate and the server-returned `capabilities.canRefresh` are both true. The API independently authorizes `REFRESH_ASSET` for owner, admin and operator roles; viewer writes remain denied. Refresh is a distinct permission from reauthorization.

The detail view submits the internal asset reference, takes only the opaque `jobId` returned by the server, prevents a second request for an active job, and polls at most five times with a one-second interval. The user may issue a single manual status check after the bounded poll pauses. Route changes, context changes, session expiration and component destruction clear the job state and cancel pending poll delays; a response already in flight is ignored when it returns. Only mapped status text and a validated request reference are shown; raw errors and `safeError` are not rendered. HTTP 429 and 503 use safe, actionable copy.

The current API runtime still has no registered Meta asset refresh adapter. Its capability snapshot therefore returns `canRefresh: false`, so the screen clearly explains that refresh is unavailable in this environment and sends no POST. No provider, sandbox or production behavior is claimed. Synthetic confirmed identity and a synthetic enabled capability exercise only the UI/job handoff in local tests; they do not register a provider or cause external effects. M4.12 supplies local coalescing evidence only.
