# M5.04 — WhatsApp BODY template request surface

## Scope and status

Issue [#58](https://github.com/costaapps/ca_meta_app/issues/58) adds tenant-scoped listing and request creation for WhatsApp EXCLUSIVE templates. Browser requests use the internal WABA asset UUID from the authorized asset catalog. The API resolves the provider WABA ID only from the same tenant's active, verified EXCLUSIVE asset and a granted candidate `whatsapp_business_management` asset grant. It never accepts a provider WABA ID, `cUUID`, `company_uuid`, token, or global credential from the browser.

The current API provider and worker adapter registrations are disabled. The service rejects calls with `503` until an explicitly reviewed provider list adapter is configured; template creation also stays disabled until both API admission and worker dispatch are enabled together. The Graph adapter is an injection point using the existing M3.08 credential resolver and M4.01 Graph client. A future worker submission is limited to one attempt; null, thrown, timed out, or ambiguous results get at most one read-only list observation. A same-name/language candidate may predate this job and cannot establish causation, so the outcome remains `UNKNOWN` until a current provider correlation mechanism is confirmed. An accepted job means provider submission was accepted or observed, not that Meta approved the template. No Meta call or Sandbox operation was run.

No database migration or schema-version change was needed. `TEMPLATE_CREATE` uses the existing durable jobs table, transactional tenant-scoped idempotency, one attempt, and `AMBIGUOUS` effect policy.

## Local BODY request semantics

This package deliberately implements only one BODY component. The closed request accepts name, language, category, body text, and optional `exampleValues`; extra provider IDs or credentials are rejected. The local contract allows placeholders `{{1}}` through `{{N}}` in ascending first-occurrence order, allows a previously-seen placeholder to repeat, and requires one non-empty example for each distinct placeholder in order. A body without placeholders may omit examples or pass `[]`. This mapping from example values to BODY placeholders is **our local contract rule**, not an assertion about current Meta requirements. Current provider limits and accepted language/category values have not been confirmed; these conservative input bounds exist for this versioned API and must be reviewed against verified capability evidence before enabling dispatch.

The UI labels a `202` as a request accepted for processing and explicitly says that this does not confirm Meta approval. A `SUCCEEDED` local job is described as forwarded to the provider, not approved. An `UNKNOWN` result advises the operator to refresh the list before another request.

For retry safety across a page reload, the UI reserves the idempotency key in `sessionStorage` before sending the request. The record is scoped by the current tenant-context reference, internal WABA asset UUID, and a SHA-256 fingerprint of the request; it stores only that fingerprint, the key, an accepted job ID when available, and a success marker, never template text or examples. Re-entering the same request in the same tab reuses the pending key. After `SUCCEEDED`, the latest success marker prevents another POST for that identical fingerprint across remounts; an edited request has a different fingerprint and can start a new job, which prunes the prior success marker. At most one succeeded marker is retained, and up to 100 unresolved attempts remain bounded by the store limit. `FAILED`/`CANCELLED` and definitive no-effect responses clear the attempt, while `UNKNOWN` and session expiry retain its key. Context changes clear attempts. Storage failures block the POST. Focused regressions simulate a lost `202` after durable enqueue and a successful job followed by same-request submissions before and after remount; the key prevents duplicate synthetic jobs.

## Security and delivery gates

- Portal session, current tenant context, and `CONNECT` authorization are checked before account resolution. The internal asset selector also requires a tenant-matched WABA, active verified asset authorization, WhatsApp EXCLUSIVE / embedded-signup journey, and the candidate management grant. Exact Meta permission mapping remains **Not confirmed**.
- List cursors and page size are bounded; results are normalized and returned with `Cache-Control: no-store`. Listing has no `channel`, number, provider ID, or caller-selected account filter beyond the internal WABA asset UUID.
- The POST body is schema/size bounded. Its idempotency key is scoped by tenant and operation, then hashed server-side; the durable job additionally hashes the canonical payload. A repeated key with different payload returns `409`.
- The worker's verified job context and current account grant are rechecked before credential resolution. A missing/unverified profile, credential, account, capability, or provider result cannot authorize a new submission. No automatic retry follows `UNKNOWN`.
- M1.08 tenant context, M3.08 credential resolution, M4.04/M4.06 Graph operation/capability evidence, and M3.12 verified asset-grant projection remain prerequisites for enabling real adapters. Adapter admission requires a reviewed change that enables the API provider and worker handler together and supplies current evidence for operation capability and tenant eligibility.

## Focused synthetic harness

Prerequisites: Node 24 and npm 11, with root workspace dependencies installed from the committed `package-lock.json` (`npm ci`). The harnesses compile/run only the M5.04 API spec and M5.04 plus route-map Angular specs, write outputs under private `.test-runs/m5-04-*` directories, and remove those outputs after the run. They make no network or Meta requests and require no database schema.

```powershell
npm run test:m5-04 --workspace=@ca-meta/api
npm run test:m5-04 --workspace=@ca-meta/web
```

Other targeted gates for the package are API/web typecheck, contract generation/check/lint because OpenAPI changed, the M1.07 generated compatibility/client checks, and `git diff --check`. Exact commands and actual results belong in the SHA-specific handoff; no full suite is implied.

## Latest focused correction

An independent review found that a request with the same fingerprint could be sent again after a local job reached `SUCCEEDED`. The UI now retains a terminal success marker without storing request text. On SHA `8470a9f9892e2f4729a4db84c9d138c0c96af253`, the focused web specs passed 8/8 and the web typecheck passed; `git diff --check` passed. The regression verifies that submitting the identical request after success, including after remount, makes no additional POST, while an edited request creates a new job with a different key. API code did not change in this correction, so API gates were not repeated.

Review then identified that unbounded success markers would consume the 100-attempt capacity. SHA `a0e8d101d8cb0fd8a942645368d93f44aa1fa0d9` keeps only the latest success marker and prunes it when a different request is explicitly reserved, while preserving unresolved attempts. The same focused web harness passed 9/9 specs, including 101 sequential synthetic successful requests with one terminal marker retained; web typecheck and `git diff --check` passed.
