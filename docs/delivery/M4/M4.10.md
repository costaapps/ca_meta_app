# M4.10 delivery handoff

## Scope and wiring

- The public callback follows the accepted `/api/v1/webhooks/meta/{appConfigRef}` route. The resolver looks up one exact `configurationRef` in the runtime environment and fails closed for duplicate matches; POST raw-body parsing and originless-request allowlisting use the same route pattern.
- WhatsApp WABA fallback is limited to account-level `account_update` change items. `history` and `smb_message_echoes` message/status items require each item's leaf `phone_number_id`; unrecognized or missing-reference items remain unmapped and quarantined. `messages` and `statuses` without `metadata.phone_number_id` carry no resource mapping and enter `RESOURCE_REFERENCE_MISSING` quarantine; the WABA `entry.id` is not used for them. The structure and availability of history, echoes, and app-state event families remain **Not confirmed**.
- Status comparison suppresses a known rank regression even when its provider timestamp is later. Unknown status ranks remain ambiguous and cannot be authorized by timestamp alone.
- `ApiModule` registers `MetaWebhooksModule` with the already-created `MetaAssetsModule` dynamic module. The webhook repository therefore uses the shared `DurableWorkDatabase`; no second connection provider is introduced.
- The central migration registry includes `META_WEBHOOKS_MIGRATION` and its four domain tables. Its stable ID is `202611060010-meta-webhooks` and its schema version is 17, following M4.03's version 16. The integrated registry contains both migrations in version order; M4.11 is expected to use version 18. Earlier migration definitions are unchanged.
- Each durable delivery stores the exact `app_configuration_ref`, provider App ID, and original environment. Replay joins the quarantined event to its source delivery and resolves that exact reference in the original environment, verifying it still maps to the persisted provider App ID. Missing, disabled, duplicate, or mismatched configuration context fails closed; provider App ID remains internal provider identity and is never used as the replay profile selector.
- `worker/main.ts` owns an explicit webhook worker lifecycle alongside the durable job worker. The lifecycle only starts with both a protected-payload adapter and an item processor. Neither adapter is installed in this runtime, so the default remains fail-closed and no webhook item is claimed.
- `apps/api/test/m4-10-meta-webhooks.integration.spec.ts` exercises concurrent status leases, stale status-fence rollback, conflicting/unknown resource quarantine, grant scoping and audited replay using synthetic data only.
- The schema change is additive and creates four webhook tables plus append-only audit triggers. No reverse migration is included; reverting application code leaves those tables and migration ledger entries in place.

## Evidence and limits

The M4.10 focused harness is `node tools/m4-10/run-focused-test.mjs`. It compiles to a unique temporary directory under `apps/api/` and removes that directory in `finally`. The database fixture is opt-in with `M4_10_MARIADB_TEST=1`; it must use a disposable MariaDB schema and deletes only its UUID-scoped rows. A successful replay leaves its append-only synthetic audit row, terminal event, and minimal tenant/app/asset mapping as durable evidence; protected delivery bytes and the rest of the fixture are removed. See [tools/m4-10/README.md](../../../tools/m4-10/README.md) for environment setup.

The implementation agent did not execute tests, builds, CI or validation, and did not install dependencies, as directed. The coordinator must record the integrated SHA, exact environment and focused gate result before treating the fixture as executed evidence.

Authored unit cases include canonical `appConfigRef` resolution and duplicate rejection, account-level WABA mapping, per-item history/echo phone-number routing and missing-reference quarantine, missing-phone `messages`/`statuses` quarantine, later-timestamp rank regression suppression (`sent@t3` after `delivered@t2`), and ambiguous unknown status ranks. The MariaDB fixture adds two profiles sharing one provider App ID and verifies replay selects the exact configuration reference saved on the source delivery while asset routing remains tenant-scoped. They remain unexecuted on this worktree.

Real Meta app configuration, app-secret retrieval, protected-payload key management/retention operations, provider callback retry behavior, subscriptions, delivery budgets and product-specific ordering remain **Not confirmed**. No Meta credential, provider call, production data or message effect is part of this package.
