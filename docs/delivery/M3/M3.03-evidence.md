# M3.03 / issue #31 — implementation evidence

## Scope and acceptance evidence

This package implements direct sign-in for a previously invited identity with an active membership. It does not create principals, tenants, or memberships. Only the in-memory fake inbox is enabled in `development` and `test`; staging and production use a disabled transport until a provider is separately approved and configured.

|---|---|---|
| GET/HEAD scanners do not consume links or create sessions | `apps/api/test/m3-03-magic-link.spec.ts`; GET renders a no-store/no-referrer explicit confirmation action and HEAD is read-only. | Browser/provider scanner matrix remains Not confirmed. |
| One-use token cannot replay, choose another tenant, or survive membership/identity revocation and expiry | Focused tests cover concurrent consume, replay, expiry, stale/revoked membership, two active tenant choices, and tenant switching through CSRF/context checks. The v14 MariaDB fixture covers proof replay, reassignment, association revocation, queued-link invalidation, append-only events, and same-principal re-verification. | The new SQL fixture is pending hosted CI; real email-proof provisioning and provider delivery remain Not confirmed. An already leased provider send may finish, but its link is consumed and cannot create a session. |
| Public errors do not expose invited-member listings | Known and unknown requests return the same accepted response; consume failures share a safe public error and no endpoint lists invitations. | Constant-time or timing non-enumerability is Not confirmed; local tests establish response equality only. |
| Rate limits and quotas prevent unrestricted delivery | Local abuse buckets cover source IP, normalized identity and tenant; queue deduplication is tested. Delivery performs at most one automatic attempt. | Limits are process-local and do not establish distributed or production quota behavior. |

## Verified email identity writer follow-up

- `apps/api/src/auth/magic-link-identity.ts` adds an internal verifier boundary. A trusted server-side email proof adapter can issue a runtime-opaque capability that contains only a keyed email hash, the server-bound principal ID, a keyed one-use proof-reference digest, the persisted revocation generation read when the proof is verified, and a short expiry. The writer rejects plain objects, missing/expired proof, malformed targets, stale generations, and any input that did not come from that verifier boundary.
- `MysqlMagicLinkStore` records the association in the existing v8 identity table and consumes the proof reference in the same transaction. The v14 append-only identity-event ledger enforces proof-reference uniqueness across replicas and stores only hashes, principal IDs, fixed event/actor/reason enums and timestamps. The v14 migration adds an unsigned generation to the v8 association row; the verifier captures it, association compares it under the row lock, and revocation increments it in the same transaction. A capability issued before revocation cannot reactivate the identity; a newly verified proof at the current generation can re-verify the same principal. Existing email hashes cannot be reassigned to another principal. Revocation requires a server-verified platform identity admin, updates the association row and appends a fixed-enum event atomically.
- The provisioner has no public HTTP controller. There is no request field that can associate an arbitrary email with a principal or tenant. The writer requires an existing active USER principal with at least one active tenant membership; it does not create a principal, tenant, or membership.
- Unit coverage is implemented in `apps/api/test/m3-03-magic-link.spec.ts` for forged/missing/expired capabilities, duplicate proof replay, cross-principal reassignment, stale pre-revocation capabilities, generation increment, revocation, and same-principal re-verification at the new generation. A synthetic MariaDB fixture is implemented in `apps/api/test/m3-03-magic-link-identity.integration.spec.ts` and wired into `tools/m2-05/run-mariadb-tests.ps1` with an isolated database and append-only cleanup by disposal of that test database. These follow-up tests and the v14 migration have **not yet been executed**; the coordinator will record exact-SHA commands and results before package integration.
- The trusted verifier implementation and the real source of `email_verified`, principal invitation binding, provisioning flow, provider email delivery, domain and browser/provider timing remain **Not confirmed**. Only local synthetic verifier fixtures exist. No production email provider or real identity data was used.
- The retention period and legal basis for the new append-only identity-event ledger are **Not confirmed**; it records only identity and proof hashes, principal IDs, fixed event metadata and timestamps.
