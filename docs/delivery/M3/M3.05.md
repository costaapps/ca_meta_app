# M3.05 / issue #41 — Suite4 embed and OAuth return

## Scope and contracts

This package implements a versioned `postMessage` contract, a browser client for the M3.02 pre-auth/ticket exchange, a guarded server-status read boundary, an opaque OAuth return signal, and exact-origin runtime/CSP configuration. The accepted M3.02 `requestId` remains in every correlated parent message together with `correlationId`; `version` and `nonce` are mandatory. The client never selects identity or tenant from parent data.

| Issue criterion | Implementation/evidence |
|---|---|
| Ready/bootstrap/ack handshake validates version, nonce, correlation, origin and source | Closed schemas and validators in `apps/web/src/app/core/embed/embed-contract.ts`; event handlers in `embed-bridge.service.ts`; focused hostile source/origin/nonce/correlation and extra-field tests. |

No Meta credential is accepted in protocol messages. |
| Popup or top-level OAuth, correlated with server onboarding state | Launch URLs require HTTPS and a configured exact provider origin. Popup signals require the tracked popup `event.source`, exact portal origin and matching opaque onboarding ID. `GET /api/v1/onboarding-sessions/:id` is session guarded and passes only the verified session, ID and tenant-context reference to an injectable read port. |
| Callback cannot prove success | `/oauth/return` strips callback query parameters from history and signals only `{type, onboardingRef}`. The iframe reports success only after the API returns a closed-schema status with matching ID and both `status` and `readiness` equal to `READY`. `auth_success=true` and `FINISH` have no success path. |
| Blocked/closed popup, expiry, tenant context change and third-party storage | Popup failure/close and expired session return to accessible top-level recovery; pre-auth/session embed cookies use `Secure; SameSite=None; Partitioned` and failure to confirm `/session` enters top-level recovery. No parent field can replace the server-issued tenant context. A context mismatch/expired session cannot confirm onboarding. |
| Resize/theme/navigation and frame ancestors | Theme is enum-validated, resize is clamped, navigation maps fixed route enums to local paths, and popup launch accepts only configured origins. | No secrets/tenant selection in messages or telemetry | Closed message schemas reject additional keys; callback strips URL params; client only handles short entry ticket and opaque onboarding ID. No localStorage or browser tenant selector is introduced. |

`API_ALLOWED_ORIGINS` continues to enforce exact portal-origin `Origin`, same-host and Fetch Metadata on browser API mutations. For a fetch from the child document to its same-origin API, the request origin is the portal child origin; the Suite4 ancestor is separately constrained by the deployed `frame-ancestors` policy, configured client allowlist, and exact source/origin checks on `postMessage`. No client-supplied `parentOrigin` participates in CORS or authorization. Real browser/Suite4 origin behavior remains **Not confirmed** until an authorized environment test.

## Server status-store boundary

The API route and injectable `OnboardingStatusReader` are present, but no persisted onboarding-state store is available in M3.05's base. The default reader deliberately returns 503. The synthetic test injects a server reader and proves that only a matching API status can confirm success; production/runtime success remains unavailable until the later onboarding package wires an authoritative reader. This is an explicit dependency, not evidence of a live provider callback.

## Configuration and setup

`API_SUITE4_EMBED_ORIGINS` and `WEB_SUITE4_EMBED_ORIGINS` are separate, exact HTTPS origins and must match operationally; the API list disables embed pre-auth when absent, while the web list disables the client and causes CSP to deny all frame ancestors when absent. `WEB_PUBLIC_META_AUTHORIZATION_ORIGINS` independently allowlists provider authorization origins. Wildcards, paths, non-HTTPS values and duplicates are rejected. No literal production origin or real credential is committed.

There are no new package dependencies; `package-lock.json` remains authoritative. Setup and focused cleanup are documented in [`tools/m3-05/README.md`](../../../tools/m3-05/README.md). Run `npm ci` and `npm run m3-05:validate` with repository Node 24.x/npm 11.x. The harness compiles only the focused API tests into a unique `apps/api/.m3-05-validate-*` folder and removes it in `finally`; web tests use Vitest, and Angular is typechecked without a broad full-suite run.

## External evidence and limits

- Suite4 origins, production config, issuer/signing keys, real OAuth/provider behavior, popup policy, parent/child browser matrix, partitioned-cookie support and real `event.source` behavior are **Not confirmed**. No Suite4, Meta or provider account/call is used by local validation.
- The issue's E2E parent-Suite4/malicious-origin/browser-device cases remain an external acceptance gate. Focused local tests exercise the protocol helpers/service with synthetic windows, origins, ticket and server state; they do not certify real browser behavior.
- The status store/callback persistence remains unavailable and returns 503 until an authoritative server implementation is connected.
- M3.06 module/schema-7 migration wiring is outside this package and must be preserved when integrated; this candidate does not modify M3.06 migration files.
