# M3.08 / issue #34 — credential resolver

Detailed implementation contract: [`credential-resolver.md`](../../meta-v2/specs/credential-resolver.md).

## Contract

The internal resolver accepts tenant, provider, app configuration, environment, asset and an allowlisted operation. It also requires a branded `VerifiedServiceTenantScope` and a server-generated correlation ID. The service rechecks `CREDENTIAL_USE` against the current tenant service grant on each resolution and again before a one-use handle enters the vault.

The caller cannot submit a credential ID, family, provider scope, grant name or fallback token. Operation policy is loaded from a server-side port using the exact tenant/app/environment/operation context. It declares the flow and auth variant, capability, asset kinds, allowed/preferred families, required asset grants/scopes, permitted verified ancestry, validity-observation age and whether an expiring credential is allowed. An absent or mismatched policy fails closed. This package does not guess Meta permissions or credential families from synthetic M1.03 examples.

Candidate reads are tenant/provider/app/environment scoped and join an asset authorization, its authorization, a credential and the vault's encrypted-record metadata. A direct grant is preferred to the nearest policy-approved verified ancestor; family preference, latest usable expiry, authorization version, credential version and internal IDs provide stable tie-breaks. Only `ACTIVE`/`PARTIAL` authorizations, active credentials, verified active asset authorizations, all required grants/scopes, a present vault record, current known health and known future or provider-declared no-expiry evidence can be selected. `REAUTH_REQUIRED`, revoked, unknown and stale evidence never become a fallback candidate.

The resolver has no cache. Resolution returns an in-process empty-object handle plus capability/family/purpose/status. A `WeakMap` keeps its binding server-side; handles are one-use, and the resolver re-reads policy, authorization, asset/grants, credential versions, health and expiry before vault use. The vault callback returns `void`; the resolver does not return the callback result or plaintext. No public controller/route was added.

Selection audit is represented by a narrow `CredentialResolutionAuditPort` containing internal actor/tenant/app/environment/asset/authorization/credential IDs, operation, purpose, family, version and selection reason only. The default provider is fail-closed until the separate M3.10 audit implementation is integrated. `APP_INSPECTION` and `CUSTOMER_OPERATION` are distinct server policy purposes; neither grants a global fallback.

## Current-schema limit

M3.06/M3.07 schema in this base stores credential family, status, version and encrypted secret, but no health or expiry observations. The MySQL resolver adapter deliberately returns health/expiry as `UNKNOWN` and the service denies use. It does not infer validity from `expires_at` absence or alter migrations. M3.09 must supply trusted, fresh observations before a database-backed Meta operation can resolve. Provider grant/scope/family and actual expiry/revocation behavior remain **Not confirmed**. The M3.07 vault authorization and M3.10 audit defaults also fail closed until their authorized integrations are provided.
