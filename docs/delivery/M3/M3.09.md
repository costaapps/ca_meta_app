# M3.09 / issue #37 — credential lifecycle

Specification: [credential-lifecycle.md](../../meta-v2/specs/credential-lifecycle.md). Decision: [ADR-009](../../meta-v2/adrs/ADR-009-credential-lifecycle-observations.md). Related resolver contract: [credential-resolver.md](../../meta-v2/specs/credential-resolver.md).

## Implemented local contract

Schema v13 adds metadata-only lifecycle observations and deduplicated local reauthentication intents, plus nullable authorization flow/auth context for exact policy selection. It does not store provider payloads or credential material. Resolver candidates now read health, credential expiry, and data-access expiry from the exact tenant/credential/authorization/app/provider/environment binding. Each observation needs an allowed provenance and freshness; a missing field is UNKNOWN. Resolver use fails closed for UNKNOWN, STALE, malformed, expired, and data-access-expired evidence. `VALID` maps to M3.08 `HEALTHY`; issue `lastVerifiedAt` maps to `health_observed_at`, and `last_checked_at` records the last attempt. `PROVIDER_NO_EXPIRY` is persisted by an explicit discriminator only; `expires_at = NULL` remains UNKNOWN. Data-access expiry is independent and must separately be known, fresh, and future.

`CREDENTIAL_INSPECTION` uses the existing `HISTORICAL_PROJECTION` durable lane. `CredentialLifecycleScheduler.scheduleDue()` bounds each run, initializes metadata-only rows for active vaulted credentials, excludes authorizations with unknown flow/auth context, takes one per-credential lease at a time, increments a schedule generation, and transactionally enqueues an idempotent job containing internal references and versions only. The registered handler/finalizer checks authorization, credential, secret and lifecycle versions plus exact flow/auth context, generation and lease owner/token. Jittered cadence is an operational check interval, not a token lifetime.

The worker flag is opt-in through `API_CREDENTIAL_LIFECYCLE_SCHEDULER_ENABLED`, but a flag alone is not a composed capability. The bootstrap currently has no lifecycle adapter composition and therefore registers no inspection handler and starts no scheduler loop even if the flag is true. The exact `(flow, auth, family)` policy has no default; missing/unknown values do not inspect. If the handler is invoked with a missing or transient inspection adapter, its finalizer records UNKNOWN/STALE without revocation; the default bootstrap does not register that handler. A validated EXPIRED, REVOKED, or ACTION_REQUIRED observation can create one deduplicated authorization+impact intent with child rows for exact verified credential↔asset links. Only REVOKED revokes the credential and those linked asset grants/authorizations. Only queued/retry-pending `CREDENTIAL_INSPECTION` jobs for that credential are canceled; running inspection is version/lease fenced. Other job types are not canceled here; they must run the credential resolver again immediately before their effect. The bounded internal M3.12 reader exposes active expired/action-required links and confirmed revoked links only when the exact current credential, tenant, and resource binding still match. The caller must authorize tenant and REAUTHORIZE access. No public route or notification delivery is added.

The inspection worker does not renew or replace credentials. `CredentialReplacementCasService` is an isolated local finalizer primitive, not a provider adapter or worker dependency. It checks the current authorization state/version, credential and secret versions, lifecycle version, flow/auth pair, generation and lease in one transaction before calling the vault conditional write. Synthetic tests prove current-write success and stale authorization rejection. Automatic renewal remains unimplemented; any later provider renewal requires a separate durable `CREDENTIAL_RENEWAL` job classified `AMBIGUOUS`, bounded one-attempt/no-unsafe-retry semantics, and provider-specific review. It must not be composed into the idempotent inspection job.

`ca_meta_asset_authorizations.credential_id` is now the exact resolver binding. V13 quarantines existing ACTIVE rows with NULL binding; new upserts without trusted credential evidence stay QUARANTINED. Reauthorization can bind a new ACTIVE credential to a previously REVOKED asset authorization only with trusted per-asset provider evidence and the same tenant/authorization/app/provider/environment context; bound active links cannot be rebound, and the old credential remains revoked. **Not confirmed**: a legitimate production caller that supplies credential↔asset evidence or both exact flow/auth variants from persisted onboarding/configuration.

## Issue evidence

| Criterion | Evidence |
|---|---|
| Persist issuance, token expiry, data-access expiry, health, last check and provenance safely | Schema-v13 `ca_meta_credential_lifecycle`; no raw response or secret columns. |
| Resolver does not authorize unknown, stale, or expired observations | MySQL lifecycle mapper, resolver contract, M3.08 focused resolver cases extended for independent data-access expiry. |
| Family-aware inspect/refresh/reauth decisions | Inspection/reauth policy lookup requires exact `(flowVariant, authVariant, family)` from server-persisted context. Migration v13 leaves legacy rows NULL; scheduler excludes them. `refreshEnabled` is fixed false in this package: automatic refresh remains unimplemented pending a separate AMBIGUOUS durable job and reviewed provider adapter. The current upsert accepts only a complete verified flow/auth pair from a service/system actor and rejects conflicts, but no runtime caller currently supplies both variants from persisted onboarding/config evidence. |
| Scheduled checks are bounded and durable | `scheduleDue()` applies per-run job/time caps, bounded lifecycle seeding, a per-credential SQL lease and generation, jittered next-check cadence, and transactional idempotent enqueue. The current worker bootstrap starts no lifecycle scheduler without an adapter composition; the flag alone does not schedule futile jobs. |
| Concurrent updates cannot restore stale credential state | Inspection preflight/finalizer fences observation writes; the separate vault replacement CAS checks authorization state/version, credential and secret versions, lifecycle version, flow/auth context, generation and lease owner/token. |
| Transient errors do not prove revocation | Handler reduces exceptions/missing adapters/invalid normalized data to a safe transient outcome; finalizer leaves UNKNOWN or marks STALE. |
| Reauthentication is deduplicated and portal-safe | Unique tenant+authorization-impact key, exact child resource impacts for all reauth-triggering health states, and a bounded reader returning only current internal resource references; caller-side tenant+REAUTHORIZE authorization is required. No delivery adapter or public provider response. |
| Revocation and reauthorization preserve exact resource bindings | Synthetic two-credential/two-asset fixture proves one revocation preserves the other asset/grant, confirmed revocation cancels only queued/retry inspection jobs for that credential, and trusted reauthorization binds a new active credential without restoring the old one. |
| Renewal concurrency | Isolated vault CAS proves current replacement and rejects stale authorization/version state. Automatic renewal is not implemented; a separate AMBIGUOUS durable job and provider adapter remain required. |

## Focused synthetic proof

Run `npm run test:m3-09 --workspace=@ca-meta/api` with the repository-pinned Node/npm versions and workspace dependencies installed. `tools/m3-09/run-focused-test.mjs` compiles only the focused lifecycle spec to a unique OS temporary directory and removes it in `finally`. Synthetic unit fixtures cover bounded due scheduling, unknown-context exclusion, transactional enqueue, registered read-only inspection handler/finalizer, explicit no-expiry mapping, missing-adapter fail-closed behavior, authorization+impact coalescing, EXPIRED/ACTION_REQUIRED resource impacts without revocation, bounded reader output, and isolated current/stale CAS replacement. The opt-in MariaDB fixture `m3-09-credential-lifecycle.integration.spec.ts` is run by `tools/m2-05/run-mariadb-tests.ps1` and covers migration v13, exact two-credential/two-asset revocation, queued inspection cancellation, reauth impact pagination, non-revoking EXPIRED/ACTION_REQUIRED impacts, trusted new-credential rebind, and current/stale CAS behavior with generated markers. Neither harness contacts Meta or uses a real credential/account, customer data, or external message.
