# M3.02 / issue #38 — ticket exchange contract

## Implemented boundary

`POST /api/v1/auth/exchanges` accepts the closed JSON body `{ ticket, challengeRef }`. `ApiModule.register` wires `AuthExchangeModule` to the same dynamic `IdentityModule.register(environment)` instance that supplies the M3.04 pre-auth, session issuer/verifier, abuse-limit service, and cookie writer. When issuer/key configuration is absent, the route remains registered and returns a safe 503. The top-level `POST /api/v1/auth/preauth` route remains available independently for M3.03, while `SUITE4_EMBED` is rejected pending M3.05. Global API middleware applies `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

The ticket verifier accepts the M1.06 local profile only: compact JWS, required `typ=JWT`, fixed `RS256`, trusted server-side key lookup by `kid`, exact configured issuer and audience, `purpose=META_PORTAL_ENTRY`, `ver=1`, non-empty bounded `session_iss`, `sub`, `tenant`, `roles`, `jti`, `iat`, `exp`, and `preauth_challenge`. `session_iss` is bounded metadata only; its Suite4 meaning/format is **Not confirmed** and it is not identity or tenant authority. Header URL/key-selection parameters and all unrecognized JOSE header parameters are rejected. Duplicate JSON keys, noncanonical base64url, malformed UTF-8, overlong input, weak RSA keys, invalid signatures, and out-of-profile times are rejected. The maximum configured ticket lifetime is 60 seconds and clock skew is bounded to 5 seconds.

After closed body, exact configured HTTPS `Origin`/`Sec-Fetch-Site`, request ID and client IP validation, the exchange consumes distributed IP-only `PORTAL_EXCHANGE_ATTEMPT` (20 per 60 seconds) before trusted key lookup or RSA verification. Only after signature/profile validation does it mint M3.01's runtime-branded `VerifiedIdentityAssertion` and consume `PORTAL_EXCHANGE` by IP plus verified issuer/subject. Ticket role values are validated for shape but are not copied into the session command. It verifies the matching pre-auth cookie/challenge and any prior session cookie through the server session verifier, then passes only the verified assertion, signed tenant selector, SHA-256 JTI/challenge digests, bounded ticket acceptance expiry, and verified pre-auth capability to the M3.04 session issuer. That issuer re-reads active principal/tenant membership and atomically consumes challenge/JTI while creating a session. An exact retry after a lost response (same ticket/JTI, challenge and pre-auth browser binding) can return only that same active session without creation or renewal; expired/revoked session, membership, or tenant, or a different cookie/challenge, is denied. The public response uses only current server membership context; cookie/session material goes through the M3.04 cookie writer.

## Registration port

The module is registered with a fixed `TicketExchangeConfiguration`, a `TrustedTicketKeySet` implementation that reads only server-managed trusted keys, an exact HTTPS origin allowlist, and M3.04 provider tokens for `PortalPreAuthService`, `PortalSessionIssuer`, session verification, and `AbuseLimitService`. The M3.04 cookie helper is supplied as the `AuthExchangeCookieWriter`. Its limiter's `RATE_LIMITED` result is mapped to 429 with `Retry-After`; no second counter or local fallback is created. The caller supplies the M3.04 identity module through `imports` so these provider tokens are visible. No key URL, issuer URL, secret, or claim is read from the ticket to configure trust.

The test key set is generated in-memory. No local real key set/JWKS endpoint, production issuer configuration, or Suite4 signing contract exists in this package. Actual Suite4 issuer, key publication/JWKS URL, key rotation/revocation semantics, source-session claim mapping, `roles` claim shape, tenant identifier mapping, browser handoff, and deployed cookie/iframe behavior are **Not confirmed**. The M1.06 proposal names `preauth_challenge`; Suite4 support for it is also an external gate. No Angular, URL parameter, localStorage, OAuth callback, or Meta credential handling was added.

## Focused harness

The focused unit/HTTP tests use Node's built-in `node:test` and ephemeral RSA keys. They do not require MariaDB, Docker, provider credentials, or additional packages. With Node 24.22.2 and npm 11.19.1:

```powershell
npx tsc -p apps/api/tsconfig.test.json
node --test apps/api/dist-test/test/m3-02-auth-exchange.spec.js apps/api/dist-test/test/m3-02-preauth.spec.js apps/api/dist-test/test/m3-04-session.spec.js apps/api/dist-test/test/api-boundaries.spec.js
```

The focused cases cover signed success and public DTO redaction, concurrent same-JTI calls against an atomic port fake, prior-session rotation, attempt and actor abuse-limit dimensions and denial (including no key lookup on attempt denial), unsupported/unsigned/key-URL/forged tickets, duplicate claims, issuer/audience/tenant/time/profile validation, trusted key rotation, pre-auth mismatch, Origin/Fetch Metadata rejection, membership revocation, top-level pre-auth, embed rejection, missing-config fail-closed behavior, and safe rate limits. A bounded once-per-minute store maintenance task removes expired JTI tombstones before expired pre-auth rows with no JTI child and never touches sessions. The opt-in `apps/api/test/m3-02-db.integration.spec.ts` was run once against a fresh MariaDB 11.8.8 instance bound only to `127.0.0.1`: migrations deployed and the two-connection exchange/recovery/revocation/expiry-cleanup proof passed (1 passed, 0 failed) on code SHA `20792590b51ce18a831692d1a3426e0434cd35cf` with `M3_02_DB_TEST=1`. The package used a synthetic database, separate migration/API users, and synthetic ticket keys only.

The single requested `tools/m1-06/run.ps1` attempt did not reach its harness because Docker Engine was unavailable (`dockerDesktopLinuxEngine` pipe missing; local Docker service was stopped and could not be opened by this environment). The two modified harness files passed `node --check`; no M1.06 database scenario ran. Do not retry Docker in this environment.

Crypto uses Node's built-in signature verification API; validation rules follow the JWT BCP's algorithm, issuer/subject, audience, and mutually exclusive profile guidance ([RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html), [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html), [Node.js crypto documentation](https://nodejs.org/api/crypto.html)). These general references do not confirm Suite4 behavior.
