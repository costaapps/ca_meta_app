# M3.02 / issue #38 — ticket exchange contract

## Implemented boundary

`POST /api/v1/auth/exchanges` accepts the closed JSON body `{ ticket, challengeRef }`. `ApiModule.register` wires `AuthExchangeModule` to the same dynamic `IdentityModule.register(environment)` instance that supplies the M3.04 pre-auth, session issuer/verifier, abuse-limit service, and cookie writer. When issuer/key configuration is absent, the route remains registered and returns a safe 503. The top-level `POST /api/v1/auth/preauth` route remains available independently for M3.03. M3.05 enables `SUITE4_EMBED` only when `API_SUITE4_EMBED_ORIGINS` contains an exact HTTPS parent-origin allowlist; the exact `API_ALLOWED_ORIGINS`/same-host `Origin`/Fetch Metadata gate still protects the browser API request. Embed challenges and sessions use host-only `SameSite=None; Secure; Partitioned` cookies. Global API middleware applies `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

The ticket verifier accepts the M1.06 local profile only: compact JWS, required `typ=JWT`, fixed `RS256`, trusted server-side key lookup by `kid`, exact configured issuer and audience, `purpose=META_PORTAL_ENTRY`, `ver=1`, `sub` ≤128, `tenant` ≤48, `session_iss` ≤128, base64url `jti` 16–256 and base64url `preauth_challenge` 32–128, plus `roles`, `iat`, and `exp`. `session_iss` is bounded metadata only; its Suite4 meaning/format is **Not confirmed** and it is not identity or tenant authority. Header URL/key-selection parameters and all unrecognized JOSE header parameters are rejected. Duplicate JSON keys, noncanonical base64url, malformed UTF-8, overlong input, weak RSA keys, invalid signatures, and out-of-profile times are rejected. The maximum configured ticket lifetime is 60 seconds and clock skew is bounded to 5 seconds.

After closed body, exact configured HTTPS `Origin`/`Sec-Fetch-Site`, request ID and client IP validation, the exchange consumes distributed IP-only `PORTAL_EXCHANGE_ATTEMPT` (20 per 60 seconds) before trusted key lookup or RSA verification. Only after signature/profile validation does it mint M3.01's runtime-branded `VerifiedIdentityAssertion` and consume `PORTAL_EXCHANGE` by IP plus verified issuer/subject. Ticket role values are validated for shape but are not copied into the session command. It verifies the matching pre-auth cookie/challenge and any prior session cookie without touching its idle-expiry clock, then passes only the verified assertion, signed tenant selector, SHA-256 digests of the JTI, compact signed ticket and challenge, bounded ticket acceptance expiry, and verified pre-auth capability to the M3.04 session issuer. Migration 6 adds nullable `ticket_sha256`; newly consumed tickets store only this digest, and a legacy consumed row without it cannot recover. The issuer re-reads active principal/tenant membership and atomically consumes challenge/JTI while creating a session. An exact retry after a lost response (same compact ticket bytes, JTI, challenge and pre-auth browser binding) can return only that same active session without creation or renewal; another signed ticket with identical identity/JTI/challenge/browser claims, an expired/revoked session or membership, or a different cookie/challenge, is denied. The public response uses only current server membership context; cookie/session material goes through the M3.04 cookie writer.

## Registration port

The module is registered with a fixed `TicketExchangeConfiguration`, a `TrustedTicketKeySet` implementation that reads only server-managed trusted keys, an exact HTTPS origin allowlist, and M3.04 provider tokens for `PortalPreAuthService`, `PortalSessionIssuer`, session verification, and `AbuseLimitService`. The M3.04 cookie helper is supplied as the `AuthExchangeCookieWriter`. Its limiter's `RATE_LIMITED` result is mapped to 429 with `Retry-After`; no second counter or local fallback is created. The caller supplies the M3.04 identity module through `imports` so these provider tokens are visible. No key URL, issuer URL, secret, or claim is read from the ticket to configure trust.

The test key set is generated in-memory. No local real key set/JWKS endpoint, production issuer configuration, or Suite4 signing contract exists in this package. Actual Suite4 issuer, key publication/JWKS URL, key rotation/revocation semantics, source-session claim mapping, `roles` claim shape, tenant identifier mapping, browser handoff, and deployed cookie/iframe behavior are **Not confirmed**. The M1.06 proposal names `preauth_challenge`; Suite4 support for it is also an external gate. M3.05 adds the embed client protocol and pre-auth cookie mode; its runtime origins are public allowlists, not credentials. The onboarding status route is guarded but has no persisted store wired on this base, so it returns 503 until a later package provides an authoritative reader.
