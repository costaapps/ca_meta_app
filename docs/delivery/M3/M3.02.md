# M3.02 / issue #38 — ticket exchange contract

## Implemented boundary

`POST /api/v1/auth/exchanges` accepts the closed JSON body `{ ticket, challengeRef }`. The controller is in `AuthExchangeModule`; it is intentionally not registered by `app.module.ts` in this package because the M3.04 session issuer must be integrated first. Global API middleware applies `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

The ticket verifier accepts the initial local profile only: compact JWS, fixed `RS256`, trusted server-side key lookup by `kid`, exact configured issuer and audience, `sub`, `tenant`, `roles`, `jti`, `iat`, `exp`, and the M1.06 `preauth_challenge`. Header URL/key-selection parameters and all unrecognized JOSE header parameters are rejected. Duplicate JSON keys, noncanonical base64url, malformed UTF-8, overlong input, weak RSA keys, invalid signatures, and out-of-profile times are rejected. The maximum configured ticket lifetime is 60 seconds and clock skew is bounded to 30 seconds.

Only after signature and claim validation does the verifier mint M3.01's runtime-branded `VerifiedIdentityAssertion`. Ticket role values are not copied into the session command. The exchange checks exact configured HTTPS `Origin` and `Sec-Fetch-Site`, applies the shared `PORTAL_EXCHANGE` abuse bucket using request IP and verified issuer/subject, verifies the matching pre-auth cookie/challenge, and validates any prior session cookie through the server session verifier. It passes only the verified assertion, signed tenant selector, SHA-256 JTI/challenge digests, bounded ticket acceptance expiry, and verified pre-auth capability to the M3.04 session issuer. That issuer must re-read active principal/tenant membership and atomically consume the challenge and JTI while creating or rotating the session. The public response uses only the issuer's current membership context; cookie/session material goes through the M3.04 cookie writer.

## Registration port

The module is registered with a fixed `TicketExchangeConfiguration`, a `TrustedTicketKeySet` implementation that reads only server-managed trusted keys, an exact HTTPS origin allowlist, and M3.04 provider tokens for `PortalPreAuthService`, `PortalSessionIssuer`, session verification, and `AbuseLimitService`. The M3.04 cookie helper is supplied as the `AuthExchangeCookieWriter`. Its limiter's `RATE_LIMITED` result is mapped to 429 with `Retry-After`; no second counter or local fallback is created. The caller supplies the M3.04 identity module through `imports` so these provider tokens are visible. No key URL, issuer URL, secret, or claim is read from the ticket to configure trust.

The test key set is generated in-memory. No local real key set/JWKS endpoint, production issuer configuration, or Suite4 signing contract exists in this package. Actual Suite4 issuer, key publication/JWKS URL, key rotation/revocation semantics, source-session claim mapping, `roles` claim shape, tenant identifier mapping, browser handoff, and deployed cookie/iframe behavior are **Not confirmed**. The M1.06 proposal names `preauth_challenge`; Suite4 support for it is also an external gate. No Angular, URL parameter, localStorage, OAuth callback, or Meta credential handling was added.

## Focused harness

The test uses Node's built-in `node:test` and ephemeral RSA keys. It does not require MariaDB, Docker, provider credentials, or additional packages. From repository root, with Node 24.22.2 and npm 11.19.1:

```powershell
npm run typecheck --workspace=@ca-meta/api
npm run build --workspace=@ca-meta/api
npm exec --workspace=@ca-meta/api -- tsc -p tsconfig.test.json
node --test apps/api/dist-test/test/m3-02-auth-exchange.spec.js
```

The focused cases cover signed success and public DTO redaction, concurrent same-JTI calls against an atomic port fake, prior-session rotation, abuse-limit dimensions and denial, unsupported/unsigned/key-URL/forged tickets, duplicate claims, issuer/audience/tenant/time/required-claim validation, trusted key rotation, pre-auth mismatch, Origin/Fetch Metadata rejection, membership revocation, and trusted key-set unavailability. The fake port checks the call contract; only M3.04's database concurrency test can prove the actual adapter transaction.

Crypto uses Node's built-in signature verification API; validation rules follow the JWT BCP's algorithm, issuer/subject, audience, and mutually exclusive profile guidance ([RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html), [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html), [Node.js crypto documentation](https://nodejs.org/api/crypto.html)). These general references do not confirm Suite4 behavior.
