# M3 decisions

## M3.01 identity and tenant boundary

- Follow the accepted M1.05/M1.06 model: principal identity is the exact stable `(issuer, subject)` pair; a person membership is keyed by `(tenant_id, principal_id)`; role and membership status are read from the server on each authorization boundary.
- A service principal is a distinct `kind=SERVICE` identity. Its tenant grants use `ca_meta_service_identity_scopes`; human roles do not authorize service operations. Database checks and composite foreign keys keep USER memberships and SERVICE grants on their matching principal kind.
- Tenant ID, legacy database/company IDs, asset IDs, and context references are identifiers only. A scope is minted only from a server-verified portal session plus a live membership. Every helper for an ID lookup includes the minted tenant ID in its predicate.
- The API has no identity or session routes in M2. OpenAPI already defines `/api/v1/session` and tenant switch. M3.01 supplies the Principal/Membership/context/policy service used by those routes; M3.04 owns persistent portal sessions, HTTP/cookie/CSRF/CORS/rate-limit enforcement and the controller wiring. The context service requires the current server session's context-reference hash and the presented `X-Tenant-Context`; stale references fail with a uniform `CONTEXT_CHANGED` error. A tenant switch resolves a new active membership and returns a new context version but does not reassign existing onboarding sessions or jobs.
- There is no public tenant or membership provisioning endpoint. Suite4's issuer and membership contract remain **Not confirmed**. Only an internal authenticated or audited provisioning path may create production membership; synthetic tests seed disposable data directly.
- M3.01 now exposes `IdentityAdministrationService` from `IdentityModule` as the internal invocation contract, with no HTTP controller. Bootstrap requires `VerifiedPlatformIdentityAdmin` plus a server-verified `VerifiedIdentityAssertion`; the normal tenant grant/revoke operations require a runtime-branded `VerifiedPortalSession`, current context, and live owner/admin membership. The MySQL adapter rechecks actor authority under transaction lock and atomically writes the tenant/principal/membership change and narrow append-only `ca_meta_identity_admin_audit` ledger row. Audit rows contain actor/tenant/principal references, fixed `reasonCode`, idempotency key and request hash, never external subject or credential material. Owner may grant `admin`; admin/operator may not. Admin may grant only operator/viewer and cannot revoke owner/admin.
- Bootstrap also inserts the exact legacy `IdDatabase + IdCompany + environment` mapping in that same transaction and idempotency unit. These are opaque scoped identifiers, not identity or membership proof; production catalog ownership/mapping authorization remains **Not confirmed**. The role CHECK only accepts the four persisted human roles. Grant operations cannot demote an existing owner/admin; only a distinct, audited revocation can remove a membership.
- `AuthorizedTenantScope` is runtime-opaque in the context service module: only current request/job resolution mints it in a private `WeakSet`; public helpers can validate but not mint. The raw identity-administration repository provider/token is not exported from `IdentityModule`; other modules receive only the policy service.
- Membership listing takes a runtime-verified portal-session capability and derives the principal from it; callers cannot select a principal ID. Service-scope resolution takes only a runtime `WeakSet`-verified service-credential capability, and the service scope itself is privately minted and runtime-verified. M3.08 must supply the trusted credential verifier adapter; its credential format, issuer and production provisioning remain **Not confirmed**. Job authorization accepts only a `VerifiedPersistedJobContext` issued after a trusted store loads the authoritative persisted job row; raw queue payload tenant/principal IDs are rejected. These verifier/store interfaces are integration boundaries, not public credentials or identity proof.
- First-tenant bootstrap is fail-closed until a server-side issuer verifier is configured and an explicit `PLATFORM_IDENTITY_ADMIN` authority is issued. The operator identity, Suite4 issuer, verifier key/claims, external bootstrap procedure and production configuration are **Not confirmed**. A configured allowlist alone does not mint identity assertions; no request/CLI value may supply a UUID, email, actor role or tenant authority. Local fake verifiers exercise the path only for synthetic tests. M3.02/M3.04 can call the internal service after wiring their actual verifier/session adapters.
- `IdentityDeniedError` currently reaches the shared safe exception filter as HTTP 500. M3.04 must map `ACCESS_DENIED` to the established access-denied response and `CONTEXT_CHANGED` to the context-changed response while retaining the safe envelope and avoiding identifier disclosure.
- M3.01 denial transactions roll back without persisting a security event. M3.10 must add the contract-required safe authorization-denial event path without leaking cross-tenant identifiers.
- Adding migration version 4 updates the executable M2.03 restore assertion and M2.07 current-schema smoke expectation. This keeps those existing consumers aligned with the new migration ledger without changing their acceptance criteria.

## M3.02 ticket exchange and bootstrap boundary

- The API wires the M3.02 exchange to one `IdentityModule` instance: the M3.04 pre-auth service, session issuer/verifier, abuse-limit service and session-cookie writer remain the runtime providers. Public RSA keys are configured on the server by unique `kid`; a ticket cannot select a URL or key source. Issuer, audience, and at least one public key are all-or-none. If all are absent, unrelated API routes still start, the pre-auth endpoint remains available for the independent direct-link flow, and exchange returns a safe 503 without issuing a session. Partial or invalid configuration rejects startup with field names only.
- `POST /api/v1/auth/preauth` creates only a top-level browser binding, is exact-origin/Fetch-Metadata protected and consumes the `PORTAL_PREAUTH` IP quota. It returns the challenge reference and expiration, while the browser cookie remains HttpOnly and is never placed in JSON. It does not assert identity or membership. `SUITE4_EMBED` is explicitly reserved and rejected until M3.05 implements the distinct parent/window handshake and recovery behavior.
- Production/staging exchange origins remain exact HTTPS origins and use the existing same-origin middleware. The local HTTP loopback allowance is derived only from `NODE_ENV=test`; no development or production bypass is enabled. This profile does not certify real Suite4 claims, key ownership/rotation, origins, or browser cookie behavior.

## External evidence

Local issuer, principal, tenant and membership fixtures prove only code behavior for those inputs. They do not establish the Suite4 subject mapping, active membership, roles, cookie topology or deployed business ownership. Meta permissions/assets and staging operations are not exercised by M3.01.
