## Reproduction

The worktree dependencies were installed once with `npm ci --ignore-scripts` (about one minute). The harness compiled the API test tree on each recorded runner invocation. From repository root in PowerShell:

```powershell
$nodeRuntime = Join-Path $env:LOCALAPPDATA 'ca-meta-runtimes\node-v24.22.2-win-x64'
$env:Path = "$nodeRuntime;$env:Path"
$env:M6_NODE_RUNTIME_DIR = $nodeRuntime
powershell -ExecutionPolicy Bypass -File tools/m6-03/run-mariadb.ps1 -TestNamePattern 'M6.03 clamps attempt duration'
powershell -ExecutionPolicy Bypass -File tools/m6-03/run-mariadb.ps1
```

The first command was the focused clock-regression run after the change; it passed 1/1. The second command ran the full profile after correcting one test-only active-count decrement; it passed 2/2 (the regression and profile), exit code 0. On the successful full run, Compose project `m603-64124e40f42847ebb60566e20e50f9fd` reached MariaDB health, migrations verified through v26, and the script removed that project's container, network and volume. No `m603-*` container or harness process remained afterward. The first full-profile attempt exposed the negative-duration DB underflow described below; after its fix, another full attempt completed the workload but failed at a harness counter that used a stale captured value when overlapping jobs finished out of order. The counter was corrected and the profile was then run once more successfully. The only product-code change is the clock-duration guard described below.

## Profile and measured envelope

The fixed input profile in `tools/m6-03/scenarios.json` uses four tenants and four synthetic assets per tenant, eight worker loops, and a 3 ms synthetic handler delay. The noisy tenant has 240 historical projection jobs; each of the other tenants has 64. Every tenant has 20 synthetic inbox events and four onboarding jobs:

| Work class | Noisy tenant | Each regular tenant | Total |
|---|---:|---:|---:|
| Historical projection | 240 | 64 | 432 |
| Inbox/webhook processing | 20 | 20 | 80 |
| Onboarding | 4 | 4 | 16 |
| **All jobs** | **264** | **88** | **528** |

Successful full-profile output, from the local API/database integration run:

| Measurement | Count | p50 | p95 | p99 |
|---|---:|---:|---:|---:|
| Enqueue or inbox persist+enqueue | 528 | 53.90 ms | 108.71 ms | 166.74 ms |
| Inbox persist+enqueue | 80 | 77.88 ms | 176.32 ms | 201.94 ms |
| `claimNext` (includes 8 empty worker polls) | 536 | 78.17 ms | 139.65 ms | 158.62 ms |
| Finalize | 528 | 9.49 ms | 16.23 ms | 19.50 ms |
| Queue wait, job creation to claim | 528 | 4,956 ms | 13,570 ms | 14,482 ms |
| Urgent inbox queue wait | 80 | 1,784 ms | 3,685 ms | 3,765 ms |

All 528 jobs completed in `13,186.81 ms`, for measured worker-loop throughput of `40.04 jobs/s` in this run. Lane completion counts were 80 urgent inbox, 16 onboarding, and 432 historical projection jobs. Every tenant completed its workload; each received 20 inbox events and four onboarding jobs. Observed concurrent claims peaked at two for the noisy tenant and one for each regular tenant. The configured per-tenant active-job cap is four and the waiting-job cap is 1,000; this workload stayed below the waiting cap and did not reach the active cap.

This is a single local measurement point: eight workers, an eight-connection durable-work pool, local disposable MariaDB and a 3 ms synthetic handler. It is a reproducible benchmark envelope for that configuration, not a minimum-resource recommendation or production capacity guarantee. Host CPU/memory, saturation curves, larger business peak volumes and scaling behavior were not measured. The API ACK SLO proposal (`p95 <1s`, `p99 <3s`) cannot be assessed from these direct service/database timings because HTTP ingress and ACK were not exercised. The measured queue wait is not end-to-end event completion latency.

## Fault and recovery evidence

| Scenario | Result in this harness | Boundary |
|---|---|---|
| Semantic inbox redelivery with a new receive timestamp/correlation/protected handle | Returned duplicate; no second job; all 80 fixture inbox rows reached `PROCESSED` | Local InboxService/MariaDB boundary, no HTTP ingress |
| Safe inbox dependency failure and retry | Retry reclaimed at attempt 2, then succeeded | Synthetic dependency outcome; no provider call |
| Persisted inbox job left claimed past a 120 ms lease | Replacement claim succeeded at attempt 2 and inbox completed | Durable lease expiry/reclaim simulation; worker process was not killed in this M6.03 run |
| Projection dependency failure and retry | Retry reclaimed at attempt 2 | Synthetic enterprise outage result; no external DB outage |
| Ambiguous outbox delivery outcome | Job remained `UNKNOWN` at attempt 1 and was not reclaimed | Synthetic ambiguous result; no provider side effect |
| Clock moves backward between attempt start and finish | Synthetic future `started_at` produced raw `-996 ms`; finalizer stored duration `0`; regression passed | Database clock field injection, not a live clock adjustment |

The clock test reproduces an actual storage failure: `duration_ms` is `INT UNSIGNED`, so a negative `TIMESTAMPDIFF` raised MariaDB `Out of range`. The targeted SQL update now clamps stored attempt durations and elapsed-time reads to zero. This prevents unsigned underflow. It does not make wall-clock time monotonic: a backward step may still delay lease expiry or extend an elapsed retry budget by the skew; host/database time synchronization remains an operational dependency.

## Clock-step code change

`apps/api/src/jobs/job-store.ts` now uses `GREATEST(0, TIMESTAMPDIFF(...) DIV 1000)` for attempt duration in normal finish and expired safe-lease handling, and for elapsed budget reads. The change is local to nonnegative duration calculations; schema, job policy and external contracts are unchanged. The targeted regression demonstrates the prior failure and the corrected stored value.
