# M6.08 canary and rollback preparation

Issue: [#73 — Executar canário por empresa/canal e comprovar rollback](https://github.com/costaapps/ca_meta_app/issues/73).

## Status and scope

This package prepares a structural rollout plan and a fail-closed ledger template. **No canary or rollback was executed.** The record remains `preparation-only`, `rolloutExecuted=false` and `deploymentReady=false`; real tenant, channel, asset, operator, SLO, release manifest, flag, route, backup and rollback references are absent. Production/canary effects are not authorized by the M6 task.

The structural ledger is [`M6.08-rollout-ledger.structural.json`](./M6.08-rollout-ledger.structural.json). It preserves four independent flow families and five contract variants (including both Instagram login variants) and requires four distinct Coexistence numbers by the eventual acceptance criterion. It contains no customer/tenant IDs or provider identifiers. All required evidence and owners remain **Not confirmed**.

The plan relies on M5.09's implemented control contract for tenant/channel/consumer/function-scoped writer assignments, version checks, current source snapshot reconciliation, shadow-read before writer change, and route-only cohort rollback. The local M5.09 implementation does not register a runtime adapter or prove a real pilot; its report says enterprise schema/catalog, live consumers, callback sharing, real grant provenance and external effect reconciliation remain **Not confirmed**. M6.06 release/rollback preparation and M6.07 external Meta/consumer acceptance are also preconditions; neither is treated as satisfied by a document or fixture.

The package implementation commit was originally created from `5629ff9f81401f673ef91d2de5de5e1faadaf7eb`; before PR, the candidate branch incorporated the current milestone through `05ab14af8638e11e2dd99a39b06fe4fb0f50e0d8`. No release candidate SHA or tag is assigned in the ledger.

## Rollout sequence when explicitly authorized

1. **Readiness gate:** bind an immutable, reviewed M6 release manifest; confirm M6.01–M6.07 dependencies and current required checks. Obtain actual staging/production ownership, Meta/consumer eligibility, backup, restore, service capacity, protected environment and named product/security/operations approvers. Any missing prerequisite blocks the affected cohort.
2. **Freeze the scope:** choose an explicit allow-list keyed by tenant, channel family and consumer. Do not split random request percentages across writers or share a cohort across unknown tenant/consumer boundaries. Keep unselected tenants on their current compatible legacy route.
3. **Reconcile the writer matrix:** for every scoped function (`CONFIGURATION`, `CREDENTIAL_REFERENCE`, `LEGACY_PROJECTION`, `OPERATION_RELAY`, `WEBHOOK_DISPATCH`), record the current owner, previous owner, target owner, phase and version from the source-of-truth control ledger. Unknown or stale ownership blocks activation/expansion. The M5.09 CAS and current-snapshot checks must pass for each writer change.
4. **Shadow-read:** require a current, read-only matched report for the same tenant/channel/consumer scope, complete source snapshot and zero unresolved drift. A shadow-read adapter must not send, subscribe, mutate credentials/grants or write to the destination.
5. **Canary:** enable only the exact scoped flag under a named operator and audit record. Observe onboarding, send/return behavior, credential state, subscription drift, webhook ACK, queue/backlog, projection, error rate and parity for an operator-ratified observation window. Keep credentials unchanged. Instagram Login and Instagram via Facebook Login remain separate variants; WhatsApp exclusive and Coexistence stay distinct. Eventual Coexistence evidence must cover four distinct numbers.
6. **Abort:** stop scoped activation and block expansion immediately for cross-tenant access, secret disclosure or double-send. Unknown writer ownership also blocks expansion. Latency, error, backlog and observation-window thresholds must be ratified with a functional owner before canary; no numeric threshold is invented here. Preserve compatible legacy cohorts and reconcile outcomes before retry.
7. **Rollback:** use a version-checked route/flag and writer-matrix transition to the last verified compatible owner. Confirm current route evidence and reconcile every confirmed external effect. Preserve valid changes and inbox/outbox/projection state. Never replay an `UNKNOWN` send or restore a revoked/compromised credential; rollback makes no credential, grant or subscription change. Verify recovery by resource/operation, not container health alone.
8. **Expand:** record the cohort evidence and go/no-go decision, then expand only by another explicit allow-list after owners accept the prior cohort. A full promotion ledger must have no unknown writer state and must preserve legacy service for non-migrated companies until their own transition is authorized.

## Ledger and evidence contract

| Acceptance criterion | Prepared structure | Evidence still required |
|---|---|---|
| Observe four flows and four Coexistence numbers without credential changes | Four separate flow-family records, five independent contract variants, four-number count, credential changes disabled | Authorized staging and real eligible test assets; no asset/number references are available here. |
| Rollback restores operation within the objective without losing confirmed events | Route/flag rollback, version check, external-effect reconciliation and explicit no-replay policy | Ratified RPO/RTO, backup/restore, staging rollback rehearsal, real event reconciliation and named operator. |
| No double-send or cross-tenant effect | Immediate abort triggers and scope keys are defined | Real canary evidence across authorized cohorts; a structural ledger cannot prove absence. |
| Unmigrated companies continue through legacy | Plan preserves the existing compatible path for unselected scopes | Deployed route ownership and active consumer inventory remain **Not confirmed**. |
| Promotion ledger has evidence per cohort and no unknown writer | Empty cohort/flag/writer/audit arrays and unknown-writer expansion block | Actual source-of-truth writer ledger, approvals, versioned cohort entries and operator decision. |

The validator at [`tools/m6-08/validate-rollout.mjs`](../../../tools/m6-08/validate-rollout.mjs) checks the structural contract and exercises fail-closed mutations: claiming a canary ran, enabling a scoped flag, assigning a writer or inventing an SLO threshold must be rejected.

Run once from the repository root with Node 24 or compatible Node; the check uses Node built-ins and reads the tracked JSON only:

```powershell
node tools/m6-08/validate-rollout.mjs
```

No network, database, Docker, Meta, tenant, customer, credential, production flag, route change, message or subscription was accessed or changed. The script cannot attest an external rollout. Issue #73 remains open until the authorized canary/rollback criteria have real evidence.
