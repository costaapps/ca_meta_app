# M6.05 / #68 — synthetic backup and restore evidence

## Result

The focused disposable MariaDB restore harness passed after the review updates on branch `desktop/m6-05`, based on commit `8093a351739da76f88800bd29d23d293e9adddcb`. The run used only generated fixture rows and ephemeral keys. Its test runner reported **1 test, 1 pass, 0 failures, 0 skipped** (exit code 0). The restore test took 5,527.92 ms; Node's test-run duration was 11,112.78 ms. This is local implementation evidence, not a production backup certification.

## Reproduction

Environment: Windows PowerShell, Node `v24.22.2`, npm `11.19.1`, Docker Engine `28.3.0`, MariaDB `11.8.8`. The npm workspace dependencies were installed once in this worktree with `npm ci --ignore-scripts`; no install was repeated for the final run. The MariaDB image is pinned by digest in `tools/m6-05/compose.yaml`.

```powershell
$nodeRuntime = Join-Path $env:LOCALAPPDATA 'ca-meta-runtimes\node-v24.22.2-win-x64'
$env:Path = "$nodeRuntime;$env:Path"
powershell -ExecutionPolicy Bypass -File tools/m6-05/run-restore.ps1
```

The runner compiled the API test TypeScript and executed only `apps/api/dist-test/test/m6-05-restore.integration.spec.js`. No API suite or provider/worker process ran. The UUID-scoped project was `m605-a95fa3dea8e04d06a4913f882c09b30f`; its container, network and MariaDB volume were removed by the runner. The runner also removed the temporary encrypted artifact directory. A post-run Docker listing for this project and volume was empty.

Measured observations for this fixture only: source-commit-to-dump-command-invocation lag `0.12 ms`, logical dump `585.99 ms`, encryption `1.66 ms`, import `2,594.78 ms`, and restore procedure `3,587.93 ms`. The lag is measured immediately before invoking the dump process; it is not a database snapshot timestamp or an observed snapshot consistency boundary. These values do not ratify the proposed 15-minute RPO or 60-minute RTO and are not service-level objectives.
