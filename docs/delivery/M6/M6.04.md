## Delivered signal contract

The API exposes a bounded Prometheus text registry at `GET /internal/metrics`. The route returns 404 when `API_OBSERVABILITY_METRICS_TOKEN` is absent; when configured, a bearer secret of at least 32 characters is required and compared using a constant-time digest comparison. The route is excluded from the public `/api/v1` prefix and remains `no-store`. Put it behind the authorized internal scrape network/TLS policy; no ingress ACL, scrape job, retention policy or receiver is configured by this package.

Tracked metrics contain only fixed route groups, methods, status outcomes, four product flows, approved Meta operations/categories, environment and webhook outcome counters. They exclude tenant IDs, asset IDs, onboarding/job references, provider IDs, phone numbers, request/correlation IDs, tokens, headers and payloads. Unknown/uninstrumented operational sources are emitted as `ca_meta_observability_source_available{signal=...} 0`; this means unknown/unavailable, never zero backlog or healthy status.

HTTP request completion logs include generated `requestId`/`correlationId`, a safe route template, status, duration and finite outcome. Client-supplied correlation headers are ignored. Meta Graph result logs include the validated operation correlation ID plus product, environment, operation, safe category and outcome. The redaction layer uses a closed allowlist and rejects non-UUID correlation references. stdout access controls/retention are not configured or confirmed. Onboarding/job/asset internal IDs and callback→job→Graph→outbox→destination propagation are not yet logged end-to-end; authorized tenant diagnostic drilldown remains the only supported per-tenant view.

Webhook ingress measures accepted/rejected requests and aggregate received/inserted/duplicate/quarantined items; item labels are named `item_type`. Monotonic latency starts in the request-context middleware before raw-body/JSON parsing and is recorded with the outcome only when the HTTP response reaches Node's `finish` event. A missing early timing context omits that histogram/ACK sample instead of reporting controller-only time. `finish` confirms the API completed writing the response locally; it does not prove the provider/client received it or include reverse-proxy/network time. Requests terminated before `finish` do not produce completed-request metrics. The last successful ACK timestamp remains per process and resets on restart; the inactivity alert aggregates the latest ACK per environment to avoid paging on an idle replica while another replica is receiving traffic. Inactivity alerting stays disabled until a deliberate baseline is supplied through `API_OBSERVABILITY_EXPECTED_WEBHOOK_INTERVAL_SECONDS` (integer seconds; `0` by default).

## Proposed SLOs

These definitions are for review and measurement planning; they are not ratified SLAs. The proposed functional owner is DevOps/SRE or Operations, with the individual assignee Not confirmed.

### API availability

- **Target:** 99.9% over a rolling 30-day window, proposed in the operations specification.
- **Denominator:** completed requests from `route_group` other than `health` and `metrics`, with outcome `success`, `dependency_failure` or `internal_failure`.
- **Numerator:** denominator requests with outcome `success` (2xx).
- **Exclusions:** health/readiness and scrape requests; redirects; 4xx/client validation; 401/403 auth/origin denials; 429 throttling. Those outcomes remain observable but do not consume availability budget.
- **Query:** `sum(increase(ca_meta_api_http_requests_total{route_group!~"health|metrics",outcome="success"}[30d])) / sum(increase(ca_meta_api_http_requests_total{route_group!~"health|metrics",outcome=~"success|dependency_failure|internal_failure"}[30d]))`.
- **No data:** denominator 0 is undefined and must display No data, not 100%.

### Durable webhook ACK latency

- **Target:** at least 99% of accepted webhooks receive a response within 3 seconds over a rolling 30-day window (equivalent p99 <3s as a proposed threshold; the operations spec also proposes p95 <1s).
- **Denominator:** requests whose signature/payload checks passed and whose durable inbox transaction committed (`outcome="accepted"`).
- **Numerator:** denominator requests whose Node HTTP response reached `finish` within 3 seconds from the earliest request-context middleware start, in `ca_meta_webhook_ingress_duration_ms_bucket{le="3000"}`.
- **Exclusions:** signature rejection, invalid content type/payload, unavailable app configuration/protector, and failed commits; those are separate counters/alerts and must not be mistaken for completed ACKs.
- **Measurement boundary:** this is application-process response completion after durable inbox commit. It excludes proxy/network transit and does not prove the Meta sender received the response. Requests ending before Node's `finish` event have no completed-request sample.
- **No data:** no accepted webhook during the window is undefined; use expected-activity alert only when an environment-specific interval is authorized/configured.

### Expected activity

No universal webhook-activity SLO is proposed. An inactivity alert compares the latest per-process durable ACK across replicas (aggregated by environment) to an explicitly configured expected interval and fires after three intervals, plus 10 minutes. Before any ACK, it compares against the oldest process start in that environment. `0` disables the alert; never infer activity from a process health endpoint. This aggregation assumes the service shares one environment-level interval; multiple independent deployments in one environment need a separate service label before this rule is used.

## Alerts, dashboards and response

See [Prometheus rules](../../../tools/m6-04/alerts/prometheus-rules.yml), [service dashboard](../../../tools/m6-04/dashboards/service.json), [four-flow dashboard](../../../tools/m6-04/dashboards/flows.json), [migration coverage dashboard](../../../tools/m6-04/dashboards/migration.json), and [operations runbook](../../../tools/m6-04/runbooks/operations.md). Thresholds are initial proposals: API/Graph failure ratio >5% for 10 minutes with at least 20 observations; webhook response-finish ratio under 3 seconds <99% for 5 minutes with at least 20 accepted samples; expected silence after three configured intervals for 10 minutes; missing-source coverage after 15 minutes is informational only. Proposed role ownership is recorded per rule; a person is not assigned.

Alert receiver, secret storage, external network restriction, retention, redacted log store, and silence review tooling are not configured. Silences must be short-lived (proposed maximum two hours), justified and assigned when the authorized Alertmanager is connected. This is a runbook proposal, not an exercised control.
