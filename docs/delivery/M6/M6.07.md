Meta distinguishes Standard and Advanced Access, App Review, business verification and Tech Provider access verification. They are not interchangeable and none grants a customer asset by itself. Standard permissions/features are limited to app-role users; non-role customer access needs the applicable Advanced Access, with per-permission/feature App Review where required. Business verification is a separate developer-business gate. For business-created/claimed apps, Tech Provider access verification is independent from App Review for the listed permissions; the WhatsApp Business App onboarding documentation separately requires the provider to be a Solution Partner or Tech Provider. See the Meta references below and re-check their current wording at execution time.

Do not record raw access tokens, OAuth codes, app secrets, unredacted client/business IDs, phone numbers, message content, screenshots containing customer records, or submitted verification documents. Store evidence in an approved restricted evidence system; retain only a redacted reference, date, candidate SHA, app/config revision and reviewer/owner in the eventual issue record.

## Flow-by-flow readiness evidence

This package tracks five distinct auth variants across four product families. Each row requires its own configuration, permission mapping, customer authorization, assets and test. Instagram Login and Instagram via Facebook Login must never share tokens, scopes or an invented Page relationship. WhatsApp exclusive and Coexistence must never be merged into one proof row.

### Facebook Pages — `FACEBOOK` / `FACEBOOK_LOGIN_FOR_BUSINESS`

- **App-level proof:** exact Facebook Login for Business configuration and Graph version; permission/feature list mapped to each Page operation; App Review/access-level result for every capability exposed to non-role customers; Page subscription endpoint/fields and callback contract approved for that version. The M4.08 contract says the current app-specific Page permission mapping and subscription semantics remain **Not confirmed**.
- **Customer-grant proof:** authorized non-role customer test user completes the exact Login for Business configuration; sanitized observation shows only currently granted permissions and the Page role/tasks needed for each selected operation; revoke and reauthorize the grant and confirm the old authorization cannot remain READY.
- **Asset proof:** enumerate all Pages in the authorized scope; prove that the selected Page is from that result, bound to the same customer authorization/tenant, and supports the operation being tested. A Page `tasks` value is a role observation, not proof of an API permission. Do not use `debug_token.target_ids` or a customer-provided Page ID as the catalog.
- **Walkthrough:** select one authorized test Page; exercise only the approved Page functions; prove webhook subscription and a redacted callback round trip if the release exposes them; verify partial grant, no Page, revoke, expiry and recovery leave the flow blocked or actionable. Do not test against an unrelated customer Page.

The current Meta User Accounts reference describes Pages on which a user has a role and returns `tasks`; it also documents permission errors. It does not prove this app's permission grants or subscription semantics. Map scopes from the exact operations in this product rather than copying an Instagram or WhatsApp list.

### Instagram via Facebook Login — `INSTAGRAM_VIA_FACEBOOK_LOGIN`

- **App-level proof:** separate Facebook Login for Business configuration and exact operation-to-permission map. The public IG User reference documents a Facebook User token and, for its documented reads, `instagram_basic` plus `pages_read_engagement`; the actual scope set changes with operations. It notes additional conditional access for a Page-role scenario. Treat those names as operation-specific Meta reference requirements, not this app's approval record.
- **Customer-grant proof:** the customer authorizes the Facebook Login variant using an eligible Instagram professional account and its linked Page; capture the granted permissions for the exact feature and verify the customer can revoke/regrant without cross-using another variant's credential.
- **Asset proof:** sanitized provider observation proves the Instagram professional-account↔Page relation and the Page/Instagram assets belong to the same current authorization and customer. The local contract requires an `INSTAGRAM_TO_PAGE` relation for this variant.
- **Walkthrough:** use a non-role test identity; verify only the features permitted by current grants; test missing Page relation, partial permissions, revoked grant, expiry, subscription/webhook result and recovery. Keep messaging, comments and publishing blocked unless their exact permissions and provider behavior are separately proven.

### Instagram Login — `INSTAGRAM_LOGIN`

- **App-level proof:** distinct Instagram Login configuration, `graph.instagram.com` host/token family, current Graph version and operation-specific scope map. Meta documents the current scope names `instagram_business_basic`, `instagram_business_content_publish`, `instagram_business_manage_messages` and `instagram_business_manage_comments`; request only the names needed by the features actually shipped and attach their own review/access evidence.
- **Customer-grant proof:** a customer-authorized Instagram Business or Creator account completes this exact login variant; record its scopes and revocation state. Do not use a Facebook User token or Page grant as a substitute.
- **Asset proof:** prove the professional account and grant are owned by this exact authorization. This direct variant has **no Page relation**; a Page requirement copied from Facebook Login would be incorrect.
- **Walkthrough:** exercise only the app-approved direct-login features with a non-role test identity; prove no Page lookup is used; test permission denial, revoke, expiry, webhook and recovery. Meta's public direct-login setup does not require a linked Facebook Page and lists ads/tagging limitations; document any product consequence.

### WhatsApp Cloud API exclusive — `WHATSAPP_CLOUD_API` / `WHATSAPP_EMBEDDED_SIGNUP`

- **App-level proof:** exact Facebook Login for Business Embedded Signup configuration, current Embedded Signup version, selected Cloud API product, callback HTTPS/allowed domains, webhook topics and the operation-to-permission map. The current v4 Cloud API reference lists `whatsapp_business_management` and `whatsapp_business_messaging` with Advanced Access; Meta now lists v5 as the latest Embedded Signup version, so verify the actual v5 configuration instead of assuming the v4 screen or version is what this app uses.
- **Customer-grant proof:** an authorized business admin completes the standard Cloud API onboarding and explicitly grants the app access to the selected WhatsApp account/Messaging account and business phone. Record selected account/phone and consent evidence as pseudonymous references, not raw IDs or codes; observe registration state from the authorized server/provider path.
- **Asset proof:** prove the customer owns/controls the WhatsApp account and phone-number asset, the phone belongs to the selected account, the grant covers each operation and the account/phone states are eligible. Where normal phone registration is required, confirm the state and protected PIN path first; never copy a PIN into the checklist. Do not borrow a Coexistence grant or infer registration success from signup FINISH.
- **Walkthrough:** on an authorized isolated test account and dedicated consented recipient, exercise onboarding, server-side code exchange, asset discovery, subscription, inbound callback, only the message/template behavior the candidate ships, revocation and recovery. A real send must wait for the responsible operator's specific authorization and approved test plan; it is not part of this preparation package.

### WhatsApp Business App Coexistence — `WHATSAPP_COEXISTENCE` / `WHATSAPP_BUSINESS_APP_ONBOARDING`

- **App/provider proof:** current Tech Provider or Solution Partner qualification; distinct Facebook Login for Business Embedded Signup configuration; exact current version, product permissions, session-info/event contract, webhook subscription and server exchange. The M4.05 adapter remains disabled and its docs predate Meta's current Embedded Signup changes. Meta lists v5 as current (released 2026-10-20); v2/v3 were deprecated 2026-10-15, and the older `only_waba_sharing` v2 feature's support window ended 2026-11-16. The v5 session object uses `messaging_account_ids`, `primary_waac_ids` and `is_on_biz_app`, unlike the former `waba_id`-only shape. Reconcile this contract in the responsible M4 package before enabling anything; this M6.07 document does not implement or certify that migration.
- **Customer-grant proof:** the customer controls the existing WhatsApp Business App number, grants the exact provider business access through its Coexistence flow and explicitly decides whether to share chat history. Capture the app version/eligibility observation, consent choice/time and corresponding authorized account/phone grant as redacted references. Meta's public guide lists Business App v2.24.17+ and a Tech Provider/Solution Partner as requirements; app-specific and customer eligibility are still **Not confirmed**.
- **Asset proof:** prove the existing Business App number and WhatsApp/Messaging account relation via the exact version's server-side contract; prove the same authorized customer and tenant own the grant; verify the correct Coexistence session and subscription. Never infer these from QR completion, browser events or a manually supplied phone number.
- **Walkthrough:** use one authorized test number, test the existing WhatsApp Business App and the API together, verify inbound/outbound mirroring and callback behavior, and check the agreed history-consent/retention result. Verify customer-facing limitations from current Meta docs, including supported features and companion-device behavior. Coexistence must not call conventional `/register`, deregister, delete or replace the phone; a failed eligibility/provider step is an escalation, not permission to perform destructive cleanup.

## Suite4/Msg4, product policy and operating practice

Before M6.07 can be accepted, the Suite4/Msg4 owners and operation owner need one joined walkthrough using a real, authorized **test** identity and company, not an app administrator/tester. It must prove:

1. The configured issuer, audience and key rotation used by the embed; a bad issuer, bad audience, expired/replayed ticket and revoked identity fail closed.
2. Active membership and company context are obtained server-side and rechecked on tenant switch; removing membership immediately blocks further session/action requests. Browser storage, URL, parent messages and `cUUID` are never authority.
3. Iframe/embed origin, return route, cookie and popup behavior are tested on supported browser configurations, both embedded and standalone; real consumer behavior is tied to the candidate SHA.
4. Msg4 receives only the agreed response/readiness semantics; a callback, QR, redirect or HTTP 202 does not become a successful connection until server-side status confirms it.
5. Credential rotation/revocation, customer reconnect, app-review denial, provider eligibility failure, callback/signature failure, and an operator escalation are traced with a redacted diagnostic bundle.

The product/privacy owner must approve a purpose-to-data map for each flow, customer notice/terms, consent boundaries, history import policy, retention/deletion schedule, support access and applicable Meta data-handling/Data Use Checkup submissions. Coexistence chat-history sharing is an explicit customer decision. Do not promise group chats, disappearing/view-once messages, linked-device behavior, history period, throughput or other product capability without checking the current Meta documentation and actual app configuration. Assign a named product/legal/privacy owner before go-live.
