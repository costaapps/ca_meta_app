## Hypercare plan when the operation is authorized

1. **Set the observation scope:** record the exact release/manifest, authorized environments and channel/consumer cohorts. Obtain named Operations/SRE, Support, Security and Product owners, an escalation route and approved access before collecting production evidence.
2. **Ratify measurement:** have the functional owner approve SLO definitions, denominators, exclusions, windows and no-data behavior from the M6.04 proposals. Use signal-source status to distinguish `unknown/unavailable` from healthy zero. Do not use unratified thresholds to claim stability.
3. **Cover recurring behavior:** plan observations for token expiry/reauth, scheduled jobs, queue recovery, projection refresh, backup and restore, and other relevant periodic routines. The required duration depends on those cycles; no date or elapsed period is recorded by this draft.
4. **Keep a redacted record:** for each observation, store environment, release reference, flow/cohort scope, timestamp, signal source, outcome, action and follow-up owner in the protected operational system. Store no access token, app secret, verification code, message body or unnecessary customer identifier in this repository.
5. **Triage by operation:** use authorized diagnostics/logs and a service-generated correlation reference where available. Separate Meta/provider outcomes from internal/API, worker, queue and projection failures. If a signal source is missing, record `Not confirmed`; do not infer zero backlog or healthy credential state.
6. **Handle retries safely:** use supported, idempotent actions only after confirming the prior outcome. Treat an ambiguous send as unknown and reconcile before retry; a database restore or code rollback cannot reverse a message already sent or a Meta grant/subscription change.
7. **Escalate critical events:** cross-tenant access, secret disclosure or double-send requires immediate stop of the affected expansion and escalation under the approved incident route. The route and on-call person are not configured here.
8. **Review support and adoption:** have an authorized user and a second operator validate the user guide, connection management, reauth/disconnect support and deployment/restore runbooks. Collect approved aggregate adoption/support measures only after privacy, data scope and retention are defined.
9. **Inventory legacy dependencies:** document active callbacks, cron/jobs, Hostinger routes and global-token consumers with a period that covers relevant scheduled and reauth cycles. Keep legacy enabled until the owners verify that each consumer is no longer needed.

## Support quick guide draft

This is a safety draft, not a published user manual or a tested UI walkthrough:

- Keep Facebook, Instagram via Facebook Login, Instagram Login, WhatsApp exclusive and WhatsApp Coexistence as distinct connection paths. Select the product path shown in the approved portal; do not transfer credentials or approvals between flow families.
- Use the portal's connection status and supported add, reauthenticate or disconnect action when that function is available. The operator must not ask the user to copy/paste an access token, app secret, password or verification code.
- When a connection requests reauthentication, have the authorized account owner complete the supported provider flow. Do not edit token rows, grants or subscriptions by SQL or manually reactivate a revoked authorization.
- For a support request, collect the affected flow, approximate time, user-visible status and an existing service correlation reference if the UI exposes one. Do not request a message body, full webhook payload or secret.
- If an outbound operation has an unknown result, do not send it again until an authorized operator has reconciled the result. A container health check alone does not establish that a user-visible operation succeeded.
- If the deployed portal lacks the needed management or safe diagnostic action, record the limitation and escalate it; do not replace it with manual SQL or credential handling.

The actual portal labels, permission prompts, user review and support access are **Not confirmed**. Validate this draft with product and an authorized user before publishing it.

| No alert or no traffic appears | Check the configured source and expected-activity baseline. | Absence of data is not proof of health; the alert receiver and activity baseline are not confirmed. |
