# ADR-021 — M5.08 tenant-safe legacy metadata projection

## Status

Accepted for the synthetic local slice. Production destination DDL, catalog provisioning, mapping evidence, credentials, consumer behavior and deployed equivalence are **Not confirmed**.

## Context

Issue #63 requires durable replication of central metadata through the existing outbox, with idempotency, ordering, tenant/company isolation, recoverable destination outage, tombstone and rebuild behavior. `OutboxService` already persists its event and `OUTBOX_DELIVER` job in the caller transaction. The canonical outbox v1 envelope is strict and its existing event payloads contain opaque references. The worktree contains no confirmed enterprise schema or production destination registry. The event envelope, job schema and `OUTBOX_DELIVER` ambiguity policy are not changed.

## Decision

1. Keep outbox event and destination projection separate. The focused harness can inject a `PROJECTION_RECONCILE` scheduler and verify it adds only `{projectionRef, sourceVersion}` through the same database manager and transaction as the event and delivery job. The default `JobsModule` leaves this scheduler disabled until a matching runtime exists, so normal API traffic does not fill tenant job capacity with unhandled projection work. When a separately reviewed runtime is supplied, the handler must re-read the stored event under its tenant and load a current central snapshot before projecting. Old event payloads never supply destination IDs, rows, DSNs or secrets; replay and rebuild scheduling remain deferred.
2. Resolve a target only through a preconstructed allowlist entry matched by the exact `(legacyDatabaseId, legacyCompanyId, environment)` tuple. No request or event field can create or select a connection. Missing catalog entries fail closed.
3. Project a strict metadata-only DTO: asset/config reference, legacy opaque reference, external/display metadata, limited capability labels, version/state and tombstone. Config message text, credentials, tokens, provider raw payload and DSN are excluded by the DTO and SQL selection.
4. Store a central checkpoint keyed by `(tenant, hash(full destination tuple), central resource reference)`. Version/hash comparisons fence stale and conflicting destination writes. The injectable scheduler gives every `connection.changed` event the same tenant-wide `resourceScopeRef`, because the contract identifies an authorization and assets can be linked to multiple authorizations. This prevents concurrent snapshots for one shared asset. Automation configuration retains its stable asset scope. A divergent destination version stays pending/retryable; the source adapter reloads the current tenant-owned snapshot on retry. A lower-version tombstone cannot be marked synced over different higher-version destination content. Commit each destination-local batch transaction separately, then advance central checkpoints. Duplicate writes remain safe by version/hash.
5. Rebuild by replaying a trusted current-state scan through the same idempotent adapter, then reconcile only rows inside the exact mapped `(legacyDatabaseId, legacyCompanyId, environment)` scope. Recompute each actual hash from the projected destination columns, repair owned field/hash drift only when the trusted current version is not older, and derive expected/actual counts and hashes from the persisted fields after repair. Tombstone a stale extra only when its `CentralAssetRef` is backed by a checkpoint for the same tenant and destination; leave unknown extras untouched and report ambiguous/failed parity instead of claiming a match. Removed/revoked resources are explicit tombstones.
6. Do not configure a live worker runtime. `configuredLegacyProjectionRuntime()` stays empty until destination DDL, mapping, credentials and consumer contract are separately confirmed and reviewed. Provisional destination table names/columns exist only in the synthetic MariaDB fixture and are not created by the application migration.

## Consequences

The focused harness explicitly injects the scheduler and demonstrates atomic queue intent, tenant-wide connection-event serialization across two authorization records linked to one asset, partial/final revocation, retry with a fresh source read after a version conflict, protection against marking a lower-version tombstone synced over divergent higher-version content, per-company separation when database ID is shared, independent destination failure/retry, tenant-fenced source loading, allowlisted active grants versus revoked grants, missing parent mapping failure, both active/revocation application orders, repair of field corruption with the old hash preserved, and full rebuild ownership/count/hash reporting. The default API composition does not enqueue projection jobs while its runtime is absent. The harness does not prove production table compatibility, a deployed legacy consumer, actual mappings/credentials, source event completeness, deployed PHP equivalence, production backlog behavior, or a live worker installation. These external gates remain **Not confirmed**.

The central checkpoint migration is schema v25 after M5.06 v24 on milestone base `44ef7a4610bbaa1c3053ec0d73f66716edbc2a49`; preceding versions are #62 v21, #60 v22, #59 v23 and #61 v24. The registry and migration-unit fixture must keep this sequence contiguous. This migration creates only the central checkpoint table and does not alter enterprise destination schemas.

## Review findings and code-snapshot evidence

The independent review found multiple correctness gaps: two authorization events for one shared asset could receive different queue scopes; a destination with higher version and divergent content could silently ignore a lower incoming tombstone while the central checkpoint became synced; rebuild parity could trust a stored `ContentHash` while projected columns had drifted; and migration v25 verified columns without its key and constraints. The fix uses a tenant-wide connection-event scope, keeps divergent version conflicts pending, recomputes hashes from actual destination columns before repair or a `MATCHED` report, and verifies the v25 primary key, index, foreign key and CHECK constraints. The standard API composition also defers scheduling until a projection runtime is configured. The updated synthetic MariaDB coverage exercises two authorizations for one asset, partial/final revocation, stale destination versions, active/revocation order and corruption with the old hash retained.

Validation applies to functional code snapshot `9213c3b23a08a7112b0956607b4e164319d301dc` (documentation changes are later). On Node `v24.22.2` and disposable MariaDB `11.8.8`, the focused runner confirmed migrations applied and both selected MariaDB integration cases passed; API source/test compilation passed and the migration registry unit test passed 9/9. The filtered Node output reports 3/3 records, including the two MariaDB cases and a test-file record. The final unfiltered DB suite was not repeated after fixing its two integration findings, so no full aggregate pass is claimed for this SHA. Commands and environment details are recorded in [`tools/m5-08/README.md`](../../../tools/m5-08/README.md). Destination runtime remains disabled. Production DDL/catalog, mappings, credentials, provider/deployed consumer behavior and PHP equivalence remain **Not confirmed**.

## Rollback

Keep the default adapter absent. The application migration creates only the central checkpoint table. A rollback can remove the handler/composition and leave checkpoints for inspection; no target schema or external state is dropped. Removing the local migration from a ledger that has applied it requires the normal reviewed forward-migration process; do not rewrite a deployed checksum.
