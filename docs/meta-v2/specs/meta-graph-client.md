# SPEC — Internal Meta Graph client

Status: M4.02 implementation candidate; issue [#44](https://github.com/costaapps/ca_meta_app/issues/44). Depends on the M4.01 app configuration registry, M3.08 credential resolver and M2.05 runtime profile. This is a server-only transport boundary; it is not evidence that a Meta app, permission or real account is approved.

## Trust and configuration binding

The internal input is a closed typed endpoint, `MetaOperation`, correlation ID, one-use credential handle and server-created execution context. The context retains M3.08's internal asset UUID and a distinct `providerObjectId` resolved from that authorized asset. Object-ID routes require the resource ID to equal that server-resolved provider ID; the internal asset UUID is used only for resolver binding. This client checks the equality but does not perform the asset-catalog lookup. The first controller/adapter that creates this context must resolve `providerObjectId` from the catalog using exact tenant, app, environment and internal `assetId`, never from browser input, and add a mismatch rejection test at that boundary. The focused M4.02 test also proves a route ID that disagrees with the server-created context is rejected before credential use. The one route exception, `FACEBOOK_PAGES_DISCOVERY`, fixes its path to `/me/accounts`; it still requires the same tenant-bound internal asset and server-created context and only uses the exact Facebook Login for Business credential. No browser URL, host, path, app ID or token is accepted as authority.

Before credential use, the client resolves the exact M4.01 `(environment, flowVariant, authVariant)` configuration, matches its configuration reference, requires a graph API version marked `VERIFIED`, and requires the exact operation capability to be enabled in the bootstrap projection. It then executes all Graph pages inside one `withCredentialForContext` callback. The resolver rechecks tenant, app, environment, internal asset UUID, operation and distinct auth variant before supplying a one-use request credential. Only the Node transport builds a Bearer header; this request credential never enters the URL, result, logs or metrics. Page access tokens returned by the dedicated Facebook discovery route follow the separate, vault-owned in-memory callback described below. The client and transport independently reject unlisted hosts, methods, path templates, headers and query keys. HTTPS certificate verification is enabled, redirects are not followed, and TLS 1.2 is the minimum.

The host derives only from the registered auth variant: `graph.instagram.com` for Instagram Login, otherwise `graph.facebook.com`. The Graph API version comes only from an M4.01 version record with reviewed evidence and `VERIFIED` state. No default or guessed version is enabled.

## Typed route and result boundary

The internal route allowlist covers object status reads, flow-checked asset edges, templates list/create, comments list/reply, subscribed-app list/subscribe, message send, conventional WhatsApp phone registration, and the dedicated Facebook Page discovery method. The `owned_whatsapp_business_accounts` asset edge is limited to `WHATSAPP_EXCLUSIVE + WHATSAPP_EMBEDDED_SIGNUP`; its business ID must come from a server-resolved catalog object and must never be accepted from browser input. Endpoint and operation must agree with the capability manifest. `FACEBOOK_PAGES_DISCOVERY` is an exact `GET /{version}/me/accounts` route for `FACEBOOK + FACEBOOK_LOGIN_FOR_BUSINESS`, with fixed `fields=name,access_token,tasks` and page size 100; it accepts no free-form path, edge or query. Its `me` path is bound to the exact tenant-scoped, resolver-selected user credential and server-owned internal asset context. The route uses M4.02's bounded pagination and rejects any next URL outside the exact Graph host/version/path. Any `access_token` on a provider next URL is discarded; subsequent requests use the resolver-selected credential in the authorization header.

The Facebook Page API uses the returned Page `access_token` to obtain a Page-scoped credential. For this route only, raw Page token fields are read into a private bounded buffer and never placed in `MetaGraphCollectionResult`. After every page is validated and pagination completes, the client calls one vault-owned batch consumer in memory. The callback receives a stable server-owned onboarding `enrollmentRef`, exact tenant/app/environment/flow/auth/internal authorization asset, correlation ID and the Page records with raw tokens; it must enroll them atomically/idempotently and return exactly one opaque UUID credential ref per Page. The returned internal discovery result contains Page metadata and refs only. An incomplete page set returns `FAILED` with a safe provider error/checkpoint; no Page token is enrolled and no partial asset list is returned. Cancellation before the callback likewise does not enroll any Page token. The callback receives the abort signal and must atomically commit or abort; if the consumer reports an uncertain failure, the caller reconciles by `enrollmentRef`. Once the consumer returns a complete ref mapping, the client reports that committed result even if cancellation arrives immediately afterward. If the consumer is absent, fails, or returns an invalid mapping, the client returns only a safe credential/action-required failure; it never returns or logs tokens, callback exceptions, raw Graph payloads, or DTOs. Zero Pages returns an empty discovery result without invoking the consumer. The bounded batch is capped at 1,000 Page records. The exact grants, token eligibility and current numeric Graph version for this app remain **Not confirmed**.

`PHONE_REGISTER` is accepted only for `WHATSAPP_EXCLUSIVE + WHATSAPP_EMBEDDED_SIGNUP`, uses `POST /{server-resolved-phone-id}/register`, and accepts exactly `{ messaging_product: "whatsapp", pin: "<six digits>" }`. The registration operation has no Coexistence route. The PIN is permitted only in this request body, is removed from response fields, and is scrubbed if echoed in response text. It is never placed in a URL, metric or safe error. No API endpoint, PIN store or queue is added by M4.04; there is currently no protected tenant-scoped PIN input lifecycle, so the provisioning adapter must leave registration in a recoverable action-required state until one is supplied.

History synchronization is intentionally not implemented in this client. Route payloads are bounded JSON and reject token, secret, authorization, header, cookie, code and PIN fields except for the exact registration body above. Response objects are capped and recursively strip secret-bearing keys; error payloads are normalized without returning provider messages, headers or nested error objects.

Every result reports a safe outcome (`SUCCEEDED`, `FAILED`, `PARTIAL` or `UNKNOWN`), HTTP status where received, attempts/retries, and safe error category/code/type/trace data where validated. Code 190/HTTP 401 maps to `CREDENTIAL_REJECTED` and a reauthorization action; it does not assert that a token is revoked. Known permission-shaped responses map to `PERMISSION_REQUIRED`. This classification is conservative adapter behavior, not a confirmed complete Meta error taxonomy.

An HTTP response whose body contains a top-level `error` is never a success, including HTTP 200. Status classification does not depend on a JSON body: 400 is invalid request, 401 credential rejected, 403 permission required, 429 rate limited and 5xx transient. Provider 5xx/network errors are transient for reads. A POST timeout, transport failure, 5xx response, oversized response, or unreadable/non-object 2xx response is `UNKNOWN`/ambiguous and is never automatically resent; a caller must reconcile provider state before deciding what to do next. Explicit retryable/ambiguous booleans are included without exposing credentials.

## Paging, retries and local budgets

Collections consume provider `paging.next` only after validating exact HTTPS host, versioned path, resource/edge path, query allowlist and cursor. Query access tokens are discarded; the client reconstructs the next request with its Bearer header, safe cursor and preserved allowlisted pagination fields. Duplicate cursors, malformed URLs, cycles, item/page limits and oversized responses stop safely and return a bounded internal checkpoint. The checkpoint contains only a cursor and counts; it is internal state and must not be logged or sent to a browser.

Local defaults are bounded and configurable within hard maxima: connect 2 s, response headers 3 s, read inactivity 5 s, total request 10 s; request body 64 KiB, response body 1 MB, at most 100 pages and 10,000 items. GET retries at most twice per request with bounded exponential jitter; a collection has a total retry budget of 16. Numeric `Retry-After` hints are capped at 30 s. POSTs are never retried automatically. Concurrency is capped at 4 active calls per tenant/app and 32 process-wide. A local ceiling of 120 requests per tenant/app per minute is enforced; an allowlisted usage header may conservatively reduce available budget. These values are local safety settings, not Meta-published quotas or recommendations.

Metrics expose only operation, product flow, environment, outcome and error category. Tenant, app, asset, provider object, credential handle, correlation ID, cursor and provider message are excluded from metric labels.

## Evidence and limits

On 2026-11-06, Meta-maintained Postman collections were available for [Instagram API](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api), [WhatsApp Cloud API](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api) and [Embedded Signup](https://www.postman.com/meta/whatsapp-business-platform/documentation/du6gzjv/embedded-signup). Their examples show Bearer-header authentication, versioned Graph hosts/paths, cursor-style paging and usage headers; they inform only the adapter shape, not permission grants or exact runtime semantics. Meta's [Graph API reference](https://developers.facebook.com/docs/graph-api/overview/) error-handling, pagination and rate-limiting pages returned HTTP 429 during the same source review. Thus exact HTTP-200 `{error}` behavior, provider error-code meanings, `Retry-After` semantics and usage-header quota thresholds are **Not confirmed**. Usage headers are treated as optional hints only. Confirm actual behavior in a reviewed app/test environment before enabling a provider operation.

The Meta-maintained [Facebook API Page-token request](https://www.postman.com/meta/facebook/request/bqfxwbp/get-access-tokens-of-pages-you-manage) documents `GET /{{api_version}}/me/accounts?fields=name,access_token,tasks` with a user access token and sample Page IDs, names, Page tokens and tasks. It supports only the request/response example; the app's minimum grants, access level, App Review, user-token eligibility and numeric Graph version remain **Not confirmed**. The M4.02 route never takes browser-supplied Page IDs or credentials.

The [Meta-maintained WhatsApp Cloud API collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api) documents the registration endpoint/body, a system-user access token with `whatsapp_business_messaging`, two-step verification via a six-digit PIN, and number ownership verification before registration. It also describes a 14-day Embedded Signup registration window. The app's Embedded Signup token type, registration grant, app-specific access level/review, exact Graph version compatibility, and observed phone registration fields remain **Not confirmed**. M4.04 therefore cannot infer that an app token is eligible or that a number needs registration; absent verified registration state and an authorized protected PIN source, per-number readiness remains `ACTION_REQUIRED` or `UNKNOWN` and the adapter must not call registration. Coexistence must never use this operation.

The M1.03 capability matrix and compatibility fixture remain separate evidence. Their synthetic values do not verify current provider permissions, Graph API versions, review state or auth eligibility. All production calls remain unavailable unless M4.01 configuration and per-operation evidence are supplied and reviewed.
