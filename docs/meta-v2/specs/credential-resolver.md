# SPEC — Tenant and asset-scoped credential resolver

Status: M3.08 implementation candidate; issue [#34](https://github.com/costaapps/ca_meta_app/issues/34). Parent domain: [provider credentials and grants](./credentials.md). Contracts: [M3.06 domain tables](../03-domain-data-and-credentials.md), [M1.03 capability matrix](../meta-capability-matrix.md), and [M1.07 error catalog](../contracts/error-catalog.md). Meta scopes, grants, token families, health and expiry behavior for the real application remain **Not confirmed**.

## Input and trust boundary

The internal request contains exactly `tenantId`, `provider`, `appConfigurationId`, `environment`, `assetId` and an allowlisted `operation`. It is accompanied by a branded `VerifiedServiceTenantScope` and a correlation ID generated by the server. The tenant must equal the verified service scope, and the current `CREDENTIAL_USE` grant is checked for each resolution and again before one-use handle execution. Raw UUIDs and caller-provided scope claims do not create this authority.

There is no caller-selected `credentialId`, family, scope, asset grant or fallback. A server-owned operation policy is resolved by the complete context and declares the flow/auth variant, capability, permitted asset kinds, required asset grant names and authorization scopes, allowed/preferred families, allowed verified ancestry, health observation age and whether `EXPIRING` credentials may be used. Policy context must match exactly. Missing, malformed, mismatched or unavailable policy fails closed. Synthetic M1.03 profile values are tests, not production configuration or provider permission facts.

## Candidate eligibility

The repository loads the target asset under exact tenant/provider/app/environment context. A target must have a current verified active asset authorization under an `ACTIVE` or `PARTIAL` authorization. Candidates must be owned by an authorization and credential in the same exact context, have an active verified asset authorization for the granted asset, active credential metadata and an existing vault record. Authorization state is `ACTIVE` or `PARTIAL`; `REAUTH_REQUIRED`, `UNKNOWN`, `REVOKED`, `DISCONNECTED`, credential `REVOKED`/`UNKNOWN`, quarantined or claimed assets are ineligible.

The candidate must include every policy-required asset grant and authorization scope. Granting an ancestor is allowed only over a bounded, verified path that the policy permits: WhatsApp phone → WABA, or Instagram professional account → Page. Every edge must match the stored type/kinds and have verified provider evidence. The resolver does not infer lineage from an external ID, browser claim, shared app configuration or a token that happens to work elsewhere.

Credential health must be a fresh, provenance-backed `HEALTHY` observation (or `EXPIRING` where policy explicitly allows it). Credential expiry must be a fresh, provenance-backed future timestamp or an explicit provider-declared no-expiry observation. Data-access expiry is an independent boundary and requires a fresh, known, future timestamp. An absent data-access deadline is never interpreted as no expiry. `UNKNOWN`, `STALE`, absent, malformed or expired evidence is not proof of validity. Reauthorization creates a new candidate/version; only the grant explicitly covering the requested asset or an allowed verified ancestor can be selected.

## Selection, result and audit

There is no cache. The deterministic order is: direct grant before ancestor, nearest allowed ancestor, explicit server policy family preference, later known expiry (explicit no-expiry ranks last among expiry deadlines), newest authorization version, newest credential version, then stable internal ID ordering. If eligibility changes after selection, the one-use handle is rejected and the caller must resolve again.

The resolver returns only an opaque in-process handle and safe capability/family/purpose/status metadata. The handle contains no enumerable identifier and is accepted once by a server-side vault adapter. It is revalidated before the vault callback. The callback returns `void`, preventing a plaintext token or arbitrary callback result from crossing the resolver boundary. Public DTOs/controllers do not receive the handle, credential ID, ciphertext, nonce, authentication tag or plaintext.

Selection uses a narrow audit port with internal actor/tenant/app/environment/asset/authorization/credential IDs, operation, purpose (`APP_INSPECTION` or `CUSTOMER_OPERATION`), family, versions, correlation ID and a fixed selection reason. It accepts no token or cipher fields. Until M3.10 provides the durable adapter, the default audit port denies resolution. App inspection is classified separately; it does not provide an app/global token fallback for customer operations.

Safe failures use M1.07 codes: `ASSET_GRANT_MISSING` (`REAUTHORIZE`), `META_PERMISSION_REQUIRED` (`REAUTHORIZE`), `META_REAUTH_REQUIRED` (`REAUTHORIZE`), `RESOURCE_NOT_AVAILABLE`, `INTERNAL_SCOPE_DENIED`, `CONTEXT_CHANGED` and `DEPENDENCY_UNAVAILABLE` (`CHECK_STATUS`). They do not contain provider text or internal IDs.

## Schema and external limits

M3.06/M3.07 persist family/status/version and encrypted bytes. M3.09 adds a separate lifecycle metadata table; a missing row or missing field still maps to `UNKNOWN`, and resolver use remains denied. The resolver does not infer `expires_at`, data-access expiry, or “never” from NULL or another implicit value. The app flow/policy registry still has no confirmed production provider grant/family facts, so its default policy is fail-closed. M3.10 provides the durable selection-audit port. These integration gaps are not evidence of real provider access or behavior.
