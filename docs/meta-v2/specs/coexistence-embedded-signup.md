# SPEC · WhatsApp Business App Coexistence browser onboarding

Status: implementation boundary authored; provider adapter remains disabled. Issue: [#49](https://github.com/costaapps/ca_meta_app/issues/49). Depends on [M4.03 onboarding sessions](onboarding-saga.md) and the exact M4.01 flow configuration. Functional owner: Meta integration.

## Goal and scope

Give the portal a separate entry for adding one WhatsApp Business App number through Coexistence. Each deliberate add-number action is a distinct `WHATSAPP_COEXISTENCE` server onboarding session whose server-selected authentication variant is `WHATSAPP_BUSINESS_APP_ONBOARDING`. Existing exclusive WhatsApp setup remains on its existing route and legacy callback state; this page does not read or write `meta.pendingProduct`, `cUUID`, a phone number, a WABA ID or any provider asset ID.

The browser lifecycle and correlation boundary are implemented behind an injected provider adapter. The current adapter has no provider implementation. The exact current SDK and Embedded Signup versions, Coexistence `featureType`, event schema, event origin/source semantics, and supported Sandbox behavior remain **Not confirmed**. Until a primary-source contract and reviewed fixture establish those values, the adapter and start action remain disabled. The UI does not load the Meta SDK or call provider endpoints.

## Browser invariants

- A component-scoped service owns the current tab's in-memory attempt list. It stores no session, state, code, tenant context or provider data in local storage, session storage, URL query parameters, or a process-wide pending pointer.
- Before creating a session, the client requires an exact reviewed provider adapter contract and one enabled `WHATSAPP_COEXISTENCE` profile from the authenticated server. The API chooses the `WHATSAPP_BUSINESS_APP_ONBOARDING` auth variant and all app/config/version values.
- On the user's click, the adapter prepares its temporary browsing context synchronously before any HTTP `await`; after the server session and launch URL are validated, the adapter navigates that prepared context. A blocked or invalid preparation creates no onboarding session and is disposed on every later failure.
- Each unresolved attempt retains a distinct prepared `event.source`. The client rejects a provider context already bound to another unresolved attempt before creating a new session, so one browser message cannot satisfy two session listeners.
- The server's launch URL and opaque `state` are validated and retained only in the attempt's memory. A code is delivered only to `POST /api/v1/onboarding-sessions/{that-session-id}/authorization-code`, with the state extracted from that same server response. The code is not placed in logs, browser storage, routes, messages to Suite4, or any other request.
- Before every attempt-specific code submission, status read or recovery action, the client re-reads the authenticated portal session and requires its tenant-context reference to match the reference captured when that onboarding session was created. A mismatch sends no session-scoped request and stops background polling; the attempt remains blocked until the user restores the original context and explicitly checks status.
- The listener is installed only for that attempt and accepts a message only when `event.origin` exactly matches the reviewed allowlisted origin and `event.source` exactly matches that attempt's prepared source. The injected decoder must validate the provider's closed event schema before returning one of the application's internal normalized events. No Meta wire fields or `featureType` values are guessed here.
- A code can arrive before or after a finish signal. The finish signal only starts status polling and leaves the session listener available for a later code until server completion, cancellation, expiry or destruction. One code submission is allowed; an ambiguous network result is never blindly resent.
- A finish/QR/callback/popup-close signal never means `READY`. Only a closed, session-matching server status response with `status=READY`, `readiness=READY`, `nextAction=NONE` and the required successful saga steps is presented as confirmed.
- Cancel closes that attempt's local provider context and reads server status; it does not cancel another session or delete previous connections. Listeners and timers are removed after terminal server status, cancellation, expiry and component destruction.
- An ambiguous session-create response blocks another create in the current page instance. This avoids minting a second idempotency key after a possibly accepted create.
- `PARTIAL` is not terminal for the browser lifecycle. Its `nextAction` and per-step statuses remain attached to that session; the page continues status polling and blocks another number while recovery or an unresolved status is present.
- Only server-provided `nextAction=RESUME` with a downstream `RETRY_PENDING` step exposes a matching `RESUME` action, and only `nextAction=RECONCILE` with an `UNKNOWN`/`RUNNING` step exposes a matching `RECONCILE` action. Authorization exchange cannot be resumed. Unsupported next actions remain informational and never trigger a provider relaunch.
- Server-provided `nextAction=REAUTHORIZE` exposes an explicit retry only after a fresh status read confirms `status=PARTIAL`, `readiness=PARTIAL`, and the authorization step is `FAILED`. M4.03 does not accept `REAUTHORIZE` at the `/actions` endpoint: the client creates a new `WHATSAPP_COEXISTENCE` onboarding session with the enabled server profile, then launches that session through the injected adapter. It requires the tenant-context reference captured by the original attempt; after a tenant-context switch, reauthorization makes no create request. Its `Idempotency-Key` is deterministically derived from the prior onboarding reference and reused for every retry of that reauthorization, so concurrent tabs acting on the same session share the server's tenant-scoped idempotency record; payload/config disagreement fails with the API's idempotency conflict. The key is sent only to the API and is never persisted. If the prior reference cannot produce a valid key under the M4.03 length/character limits, the reauthorization action stays unavailable. The prior session remains in history and is associated only with the replacement onboarding reference; no phone/WABA number is inferred or correlated.
- This idempotency prevents duplicate replacement sessions only when tabs are acting on the same prior onboarding reference. M4.03 has no server claim keyed to a logical phone/add-number intent, and the browser cannot identify that intent before provider authorization. Two distinct prior session IDs can therefore still create distinct replacement sessions; preventing that case requires a reviewed server-side claim/idempotency contract and is not asserted by M4.05.
- Recovery posts only `{action, stage}` to `POST /api/v1/onboarding-sessions/{id}/actions` with the current portal session, tenant context, CSRF token and a fresh idempotency key. HTTP 202 means queued, not completed. The action remains visible as pending while the authoritative status reports its stage in flight; another action or number is not started until a later status confirms a safe terminal state.
- A local popup close or client timeout cannot release the number slot. If status still reports `PARTIAL`, readiness is `UNKNOWN`, or a step remains in progress, the attempt remains pending. A fresh server-confirmed `REAUTHORIZE` may replace only that failed authorization attempt with a new server session; the replacement then blocks further numbers until its status confirms `READY`, `CANCELLED`, `EXPIRED` or `FAILED`.

## Endpoints and security

The client first reads the authenticated `/session` and `/integrations/flows` endpoints with credentials and the current tenant-context reference. A create action requires a readable CSRF cookie matching the M3.04 request guard and sends `X-CSRF-Token`, `X-Tenant-Context`, and a fresh `Idempotency-Key`. No `cUUID` is sent or used as membership authority. The authorized API resolves tenant and principal from the portal session.

After the server flow profile is enabled, the create request is exactly:

```json
{
  "flowVariant": "WHATSAPP_COEXISTENCE",
  "requestedCapabilities": [],
  "returnRoute": "setup"
}
```

The actual `requestedCapabilities` are copied from the enabled server profile, not inferred in the browser. Code submission uses the existing M4.03 endpoint and its same-session CSRF/context/idempotency requirements. Status is read from `GET /api/v1/onboarding-sessions/{id}`; no browser claim can set a server status.

## External evidence and acceptance

The accessible [Meta WhatsApp Embedded Signup Postman collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/du6gzjv/embedded-signup) supports general Embedded Signup JavaScript SDK/Login and App Review material. It does not establish the current Coexistence SDK/version, `featureType`, postMessage payload, origin/source rules, QR/FINISH semantics or Sandbox eligibility. Direct official documentation pages were inaccessible during this research. These items stay **Not confirmed** and block the provider adapter, QR completion and real-Sandbox acceptance. The local adapter port prepares a user-click-bound browsing context before server requests so a later reviewed popup adapter can preserve browser user activation without guessing provider behavior.

The authored focused synthetic tests exercise only this application's normalized adapter boundary, exact origin/source comparison, user-gesture preparation order, code-to-session endpoint routing, finish-before-code order, server-only READY decision, four consecutive session-history entries, `PARTIAL`→`RECONCILE`→`RESUME`, direct `PARTIAL`→`RESUME`, and the status-gated `REAUTHORIZE`→new-session path with a stable per-source-session idempotency key. Tenant-context-switch cases verify that code submission, status reads and recovery stop before the session endpoint when context changes. Other fixtures cover pending recovery/status gating, cancellation/timeout blocking, and two service instances with distinct message sources. They do not claim to reproduce Meta's event schema or real SDK behavior and were not executed by the implementer. A later change that supplies a provider decoder must attach a current official source, exact version/config contract, sanitized provider fixture, and review; then the package must run its browser/unit gates and authorized Sandbox scenario.
