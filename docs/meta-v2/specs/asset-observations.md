# SPEC — Versioned Meta asset observations

Status: M4.12 implementation candidate; issue [#54](https://github.com/costaapps/ca_meta_app/issues/54). Related contracts: [asset catalog](asset-catalog.md), [Meta subscriptions](meta-subscriptions.md), and [OpenAPI asset catalog](../contracts/openapi.yaml). Functional owner role: integration Meta/backend; people unassigned. Meta field availability, permission-specific polling budgets, and a measured provider SLO are **Not confirmed**.

## Purpose and evidence boundary

Login/onboarding evidence remains separate from later asset status observations. This extension records a tenant-scoped, append-only sequence of normalized observations. It does not change authorization state, credential state, verified asset bindings, or the grant rows used by the credential resolver. A provider adapter may produce this normalized contract only after its per-flow/per-kind field list has been reviewed. The production worker currently registers no asset refresh adapter, so refresh remains unavailable and no Meta request is enabled by this package.

The only stored dimensions are the already normalized local catalog concepts: asset kind, status, grant names, subscription state, projection state, source, provider observation time, server fetch time, schema version, version, stale deadline, and bounded drift codes. Billing, quality, phone eligibility, provider payloads, tokens, and other per-kind fields are excluded until official field and permission evidence exists. Unknown provider status values can be retained only as a short enum token matching `[A-Za-z0-9_.-]{1,64}`; they normalize to UNKNOWN and never become a negative status.

## State and ordering rules

- A source may be `META_API` or `SIGNED_WEBHOOK`; fetched time is generated by the server. The adapter supplies provider/event observation time only when it has one.
- `ACTIVE`, `INACTIVE`, `UNKNOWN`, and `UNAVAILABLE` are distinct. Missing, unknown, or unavailable status does not remove an asset. An unavailable read preserves the last known normalized values, marks the relevant dimensions unavailable, and makes the status observation stale.
- Permission state is `OBSERVED`, `UNKNOWN`, or `UNAVAILABLE`. An observed empty grant list is different from a missing grant field. Grant names are bounded and normalized; a missing/unavailable list preserves prior names for diagnosis but marks its availability accordingly.
- Each asset has a monotonic append-only version. An observation whose provider time is equal to or older than the latest accepted observation is ignored. An unavailable attempt can be appended without advancing provider observation time.
- Drift codes describe status, permission, subscription, or projection transitions. They contain no raw before/after values; `PROJECTION_STALE` is emitted only when a projection enters an unresolved state, while the read model keeps `RECONCILE` actionable until it returns to a resolved state.
- A newly detected actionable drift appends one deterministic `asset.drift.detected` outbox intent in the same transaction as its snapshot. Its idempotency identity covers tenant, authorization, asset, snapshot version and the sorted drift-code set. A later observation with the same normalized drift state emits no equivalent notice; a distinct later transition can emit a new one. The event carries only an opaque notice reference, asset reference, bounded drift codes and a non-`NONE` next action. No outbox delivery handler or notification provider is installed, so the intent is durable but not externally delivered. Subscription repair remains out of scope.
- The existing 24-hour catalog freshness bound is reused as a display stale deadline. It is not an end-to-end or provider SLO; changes-real-Meta-within-SLO remains an external gate.
- A status observation never reactivates a revoked/disconnected authorization or credential. Existing authorization/credential records remain authoritative for operation resolution.

## Tenant isolation, persistence, and recovery

Migration schema version 19 adds `ca_meta_asset_observations`, keyed by `(tenant_id, authorization_id, asset_id, version)`, with composite foreign keys to both the asset and its exact authorization binding. It declares the `(tenant_id, asset_id)` foreign-key support index explicitly so MariaDB schema verification has a deterministic index shape. Writes lock and verify the tenant, authorization, and asset together, and accept observations only while the asset binding is ACTIVE and VERIFIED and its authorization is ACTIVE or PARTIAL. A late job for a revoked or inactive binding is suppressed. The table stores the normalized snapshot only and rejects UPDATE/DELETE through append-only triggers. No provider response or credential material is persisted. The migration is additive; an older API can ignore the new table during rollback, and cleanup is a future reviewed retention migration rather than destructive rollback.

Manual refresh continues through the existing durable `ASSET_REFRESH` queue. Active requests for the same tenant and asset coalesce. The adapter returns a separate normalized observation for each eligible authorization binding; the repository persists each one under its exact authorization context. After a job completes, an internal configurable per-asset admission interval (60 seconds by default) avoids repeated dispatch pressure. This is only local queue policy; it does not claim a Meta rate limit or SLO. The provider adapter remains disabled, and the existing M4.10 webhook ingress is not changed; a reviewed signed-event processor can call the same observation repository once its event mapping is confirmed.

The connection-detail catalog already scopes its asset query to one server-resolved authorization reference, so it can include that binding's latest status observation. Generic asset list/detail reads attach an observation only when exactly one active, verified authorization binding exists; when multiple eligible bindings exist, they omit the optional snapshot and report an unknown/stale aggregate where evidence exists. A future multi-binding asset view must explicitly aggregate those observations before exposing them.

## Focused harness

From the repository root, after the root `npm ci --ignore-scripts` setup:

```powershell
npm run test:m4-12 --workspace=@ca-meta/api
```

The harness compiles the focused TypeScript project into `apps/api/.test-runs/m4-12-*`, runs only the synthetic M4.12 test file, then removes only its verified child directory. It requires Node/npm already installed by the monorepo setup; it does not start MySQL, Docker, a browser, or make network calls. The command has not been run by the implementer.

## Evidence limits and next gate

The tests in `apps/api/test/m4-12-asset-observation.spec.ts` are synthetic local contract evidence only. The provider adapter, live asset permission changes, unknown real provider enums, per-kind Graph field permissions, real rate budgets, webhook delivery and measured SLO are **Not confirmed**. Before enabling a real adapter, bind each flow and asset kind to an official field/permission source, prove tenant authorization and credential selection in an authorized sandbox, and record observed latency/rate outcomes without storing provider payloads.
