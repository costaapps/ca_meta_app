## Coexistence safety and unresolved behavior

The accessible generic Embedded Signup collection describes a solution-provider onboarding path and includes ordinary phone registration. It is not sufficient evidence for the Business App/Coexistence flow. The Coexistence-specific Meta page was not retrievable (HTTP 429), so this matrix does not assert a registration procedure, history window, history payload enum, event-field set, feature type, echo semantics, or offboarding API.

**Proposed project safety policy, not a Meta-confirmed rule:** do not call the conventional phone `/register`, `/deregister`, or delete path as a Coexistence fallback, retry, or compensating action. The Coexistence adapter should stop in an actionable state until its own current Meta-documented procedure is verified. History consent, supported interval, `history`/state/echo fields, and offboarding need separate evidence and tests; no time window or enum is pinned here.

## Proposed error handling and recovery

These are local design proposals, not claims about Meta retry policy. Preserve a flow-specific attempt record with a correlation ID and redacted error category. On user cancel, retain no authorization and offer a user-initiated restart. On transient transport/429/5xx errors, use bounded backoff only for operations documented as safe to retry; if code exchange outcome is ambiguous, stop and require a fresh authorization when provider evidence requires it. On insufficient permissions, report the missing operation/grant, do not broaden scopes or switch token families automatically, and allow a new consent attempt only after the app owner confirms access. On unavailable or contradictory documentation/configuration, block that capability with a reviewable reason. For Coexistence, never fall back to conventional Cloud API registration. Exact provider error codes, retryability, state lifetime, and refresh semantics remain **Not confirmed** and must be validated per operation before implementation.
